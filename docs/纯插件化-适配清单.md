# StarHub 纯插件化适配清单(DSH bundle 形态)

> 目标形态:**StarHub 作为「一个可安装的 DSH 组合包(bundle)」**,由 DSH 自带插件页的
> **添加插件**对话框(包名 / GitHub 地址 / 本地目录,见截图)安装进任意 profile,不再依赖
> `scripts/provision-dsh.mjs` 的安装后置物化。
>
> 本文只做差距盘点与适配决策,不含实现。事实基线来自 vendored DSH(`vendor/deepseek-harness`,
> 上游 `dsh-v0.2.1-alpha.1`)与本仓库现状代码。

---

## 一、DSH 侧的安装契约(事实基线)

### 1.1 什么算「可安装的插件」

一个 npm 包只要 `package.json` 里声明 `dsh.bundle.patch`(单个路径或有序数组),它就是
**bundle**(组合包);`plugin_manager` 会把它当成 profile 的一层 patch 并选入
`dsh.profile.bundles`。没有这个字段的包会被警告
`dsh: warning: <name> declares no dsh.bundle — installed as a plain dependency, not a profile layer`
(`packages/boot/plugin-manager/src/operations.ts:98-109`)。
patch 文件必须是合法 YAML 列表,支持 `insert:` 追加行与裸 `- id:` 整段替换目标行 `config`。

最小可用 bundle(上游 skill 原文示例,`packages/preset/agent-preset/skills/cordis-plugin-development/references/host-plugin.md:5-27`):

```json
{
  "name": "@local/my-plugin",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

```yaml
- insert:
    - id: my-plugin
      name: '@local/my-plugin'
      config: {}
```

行名支持**子路径插件**(`@scope/pkg/search`),用于把多个插件塞进同一个包
(`apps/web/tests/fixtures/plugins/fixture-bundle/cordis.patch.yml:1-8`)。

### 1.2 安装动作做了什么

`installBundle(spec, {registry, approvedBuilds, requestId})` 的语义(摘要自
`packages/boot/plugin-manager/README.zh.md:40-69`、`packages/boot/plugin-manager/src/operations.ts`):

| 环节 | 行为 | 对我们的约束 |
|---|---|---|
| 前置检查 | `inspect(spec)`:注册表包走 `pnpm view`;本地绝对路径读其 `package.json`;git/tarball 仅回形式 | 本地路径安装零网络,便于验收 |
| 版本兼容门 | 安装前用 `evaluatePluginCompatibility` 比对 **`@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的 peerDependencies**;不满足则安装直接失败(`incompatible-version`)且不下载 | StarHub 现在这些 peer 全是 `workspace:^` |
| 安装 | 在 **profile 目录**里跑 `pnpm add <spec> --registry <…>`,注册表失败才按 `fallbackRegistries` 换源 | 包必须在注册表可解析 |
| 选入 | 成功后才把包名追加进 `dsh.profile.bundles`;失败/取消会恢复 `package.json` 与 `pnpm-lock.yaml` | 安装失败不留半套 |
| 构建脚本 | pnpm 11 拦下的依赖脚本要用户批准(`pendingBuilds` / `approvedBuilds`),否则安装失败 | 「安装时编译 sidecar」不可行 |
| 行级兼容门 | 只检查**本次 bundle 的 insert 行**所点名的包清单的 peer(`operations.ts:248-272`) | 行指向的每个包都要能解析 |
| 生效 | 有 HMR 的在线 profile 立即挂载;否则 `restart-required`;**替换已安装包需重启**才能换 JS 模块世代 | 升级=重装+重启 |
| 依赖解析 | 行的裸包名从「dsh 安装锚点 → profile 目录」依次解析(`packages/boot/app-boot/src/profile.ts:694-717`) | 随 dsh 出货的包(如 `dsh-tool-session-query`)不必再拷 |
| 客户端半边 | `packages/client/modules` 扫描 Loader entries 里声明 `dsh.client` 的包,取 `./client` 导出,经 `/plugins/<pkg>/client.js` 下发(`packages/client/modules/src/index.ts:2-8,840-855`) | 客户端半边对 profile 安装的 bundle 同样生效 |
| 展示元数据 | 插件页从包的 `locale/*.json`(`meta.title`/`meta.description`)与 `./icon` 导出读标题、描述、图标;缺失才回退 `package.json` 名与默认图 | StarHub 十个包目前全无 |

### 1.3 三个容易踩的约束

1. **`workspace:` 协议不可安装**:注册表与 git 安装都要 pnpm 真解析版本;本地目录安装
   DSH 官方文档明确说是「link the checkout」,被 link 的包自己的依赖不会由 profile 安装
   (`references/host-plugin.md:35`)。→ **bundle 最稳的形态是无运行时依赖、自包含**。
2. **profile 目录是安装现场**:pnpm 在 `$DSH_HOME/profiles/<profile>/` 跑;`$DSH_HOME`
   不在 dsh 安装树里,任何「相对仓库根」的路径假设在安装形态下都不成立。
3. **Desktop 组合的包管理由桌面壳负责**(`packages/boot/plugin-manager/README.zh.md:139`),
   截图那个对话框就是壳提供的入口;我们只需产出标准 bundle,不重写安装 UI。

## 二、现状:StarHub 今天是怎么装进 dsh 的

```
scripts/provision-dsh.mjs(安装后/CI 各跑一次)
├─ 物化 profile 三件套:package.json(dsh.profile.bundles=[dsh-base,dsh-web-app])、
│  cordis.patch.yml、pnpm-workspace.yaml                    provision-dsh.mjs:349-375
├─ 把 10 个包(9 插件 + bridge)的 package.json+lib/ 拷进
│  <profile>/node_modules/@deepseek-ai/dsh-starhub-*        provision-dsh.mjs:50-64,377-396
├─ 另拷闭包外依赖 dsh-tool-session-query                    provision-dsh.mjs:103,398-411
├─ 两个 sidecar 二进制 + React 工作台 dist 落到
│  <DSH_HOME>/starhub/resources/                            provision-dsh.mjs:413-424
├─ 按 id 行级合并 3 个受管行:webserver / starhub-bridge
│  (sidecarCommand 绝对路径) / starhub-host-static(windowDist 绝对路径)
│                                                           provision-dsh.mjs:84,426-449
└─ 写 provision.json 漂移清单                                provision-dsh.mjs:451-464
```

十个包全部 `private: true` + `peerDependencies: workspace:^`
(`packages/starhub/bridge/package.json:4,22-26` 为典型),patch 行住在
`examples/starhub-desktop/cordis.patch.yml`(**profile 用户层**,不是 bundle 层)。
桌面壳本身对 StarHub 零引用:上游 `apps/desktop/**` 里没有任何 starhub 字样,
`extraResources` 也不含 StarHub 资源;release.yml 里的 provisioning 只用于 CI 验证组合
(`.github/workflows/release.yml:192-202`)。

**结论:今天是「安装后置脚本 + profile 用户层」形态,不是 bundle 形态。**
按截图那条路径安装,DSH 会把我们当成普通依赖或拒绝,插件页也不会出现 StarHub 行。

**补一条更硬的事实**:`provision-dsh.mjs` 全仓库只有 `package.json:28` 的 npm script 与
`tests/provision-dsh.test.mjs` 两个引用,**没有任何被安装的应用会调用它**;`release.yml:192-202`
只在 CI 里对一个临时 `$HOME` 跑一遍以验证组合,`apps/desktop/**` 对 starhub 零引用,
`extraResources` 也不含 StarHub 资源。也就是说:**品牌安装包目前并没有自动把 StarHub 装进去的路径**
(与 `docs/去Tauri化-M4-发布链清单.md:255-265`「仍挂着的事」一致)。
→ 纯插件化不只是「换个分发方式」,它同时是**补上这条安装路径**。

> 相关既有文档:`docs/StarHub去Tauri化-迁移立项设计.md:137-146`(§五 当初就设计过
> `node_modules/<bundle>` + `dsh.profile.bundles` 路线,实现时改成了拷贝式 provisioning)、
> `docs/插件体系打通方案-dsh插件统一.md:114-117`(仓库内最接近打包规范的一条:
> `dsh.bundle` + `exports["."]` + `exports["./client"]` + `exports["./package.json"]`)、
> `docs/AI内核替换方案-deepseek-harness.md:279-302`(生态调研:198 个可 `dsh plugin add`
> 的插件全都有 `dsh.bundle`,并记着当时「不走 dsh plugin add」的立场——本文建议改判)。

## 四、需要拍板的决策

1. **单包还是多包**:推荐「**一个自包含 bundle 包**」(十行用子路径导出,客户端半边留在包内),理由是本地路径安装不装依赖、发布与版本只有一个;代价是包体大、单一 `dsh.client` 半边。
2. **sidecar 二进制怎么来**(C1):推荐 **(b) 首次运行从 GitHub Releases 下载 + 校验和**,包体保持可用;若要求离线可用则选 (a) 随包分发并按平台拆 `optionalDependencies` 风格的子包。
3. **`permission` / `session-query-sqlite` / `webserver` 三条上游行覆盖**(B2):推荐**从 bundle 移出**,改成文档化的可选 patch,避免「装插件改全局行为」。
4. **是否保留 provisioning 链路**(G4):推荐保留为「StarHub 品牌安装包」路径,同时把 bundle 定为**对外唯一插件形态**,两条链共用同一份 patch 源文件(单一事实来源)。
5. **目标平台**:Windows x64 优先,是否要 Linux/macOS 决定 C1 的产物矩阵与 CI。
6. **命名与 scope**(A3):确定对外包名与 scope,再动 manifest。

## 七、MVP 已落地(v0.129.0)

### 怎么装(今天就能做)

```bash
npm run build:window        # 工作台 dist(已有可跳过)
npm run sidecar:build       # Go sidecar(已有可跳过)
npm run sidecar-rust:build  # Rust sidecar(缺 release 时组装脚本会回退 debug 构建)
npm run build:lib           # 九个插件的 lib/(tsc host + client bundle)
npm run plugin:bundle -- --pack   # 组装 + 打 tarball
npm run plugin:publish      # 发布到注册表(需要 NPM_TOKEN / 已登录;可 --dry-run 先验)
```

**推荐:注册表安装(可原地更新)。** 发布后插件页 **添加插件** 填包名与版本:

```
@starhub/dsh-plugin@<版本>
```

DSH 0.2.2-rc.1+ 会在插件详情里显示 **Versions / Update**;更新失败会回滚到原版本。

**离线兜底:tarball 安装(无原地更新)。** `plugin:bundle --pack` 打印一个 `.tgz`
绝对路径 + 一个 Release URL,在插件页粘贴对应平台的那一个:

```
https://github.com/dabaicai001/starhub/releases/download/v<版本>/starhub-dsh-plugin-<版本>-win-x64.tgz
```

这个资产由发布链自动产出并挂到 Release 上:**推 `v*.*.*` tag 时 `release.yml` 的
windows job 顺手打包**(它本来就构建了 libs、工作台 dist 与两个 release sidecar,
同一份产物不重复构建),tarball 作为独立 artifact 上传,并与 installer 一起挂到同一个
Release。`.github/workflows/plugin-bundle.yml` 是 **workflow_dispatch 手动兜底**:装机链
因为签名/更新源 secrets(`DOWNLOAD_TEST_RELEASE_ID` 等)走不到 publish 时,手动
dispatch 一个已有 tag,插件 URL 照样能拿到。

> 早期版本让两条工作流都监听 tag,结果是同一个 tag 起两条 job、各重建一遍 release
> sidecar(各 ~15 分钟),看起来像「两个版本在打包」;v0.129.3 起合并为一条。

资产名必须带平台标记:包内是两个平台相关的 sidecar 二进制,同名资产在同一 Release 上
会互相覆盖,而用户粘的 URL 必须唯一指到本平台那一份。

> 包名那条路要把包发到 npm;git 地址那条要仓库里有构建产物,当前不可用。冒烟:
>
> ```bash
> npm run smoke:plugin-bundle -- --spec "<上面那个 .tgz 路径或 URL>"
> ```

### 仍挂着

1. **发布形态**:发到公开 npm(定 scope/包名/access),才能走「粘包名」那条路;否则只能发 tarball。
   → v0.140.5 已补:`npm run plugin:publish` + 发布链的 npm 步骤 + 可发布清单;仍需配置
   `NPM_TOKEN` 与 scope 归属,详见 `docs/DSH升级适配清单-v0.2.2-rc1.md`。
2. **平台矩阵**:Windows x64 之外是否出 Linux/macOS 二进制;若出,考虑按平台拆包或首启下载 + 校验和(C1)。
3. **可执行位**:Windows 不关心;Linux/macOS 上 tar 包的 sidecar 需要 `+x`(发布前在 CI 里 chmod 并验证)。
4. **卸载与 HMR 回收**(D5/D6):`remove_bundle` 后必须杀掉两个 sidecar、关 `/starhub/live` WS、释放路由;并验证 HMR 重载不留孤儿进程。
5. **升级体验**:从注册表安装后走插件页 Versions/Update(DSH 0.2.2-rc.1+,失败会回滚到原版本);tarball 安装仍需卸载+重装。版本矩阵与迁移说明见 `docs/DSH升级适配清单-v0.2.2-rc1.md`。
6. **展示资源**:逐行图标(现在十行共用一张 SVG)与插件页渲染目视确认。
7. **D1 冲突诊断**:profile 里同时有 `dsh-sdk-jsonrpc-server` 时的 duplicate service 要给出可行动文案。
8. **双轨**:provisioning(品牌安装包)与 bundle 是否共用同一份 patch 源、长期是否收敛成一条。
