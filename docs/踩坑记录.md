## 1. 中文输入法 + xterm.js

中文 IME 在终端中输入是已知的难点。后续实现要点:
- xterm.js 的 `onData` 事件拿到的不是 IME 合成后的最终文本
- 需要监听 `keydown` 而非 `onData` 处理输入法
- 设置 `applicationCursor`、`applicationKeypad` 模式按需
- 持续在 Linux / macOS / Windows + 搜狗/微软/QQ 输入法下测试

## 2. ZMODEM 协议

v0.17.0 使用 `zmodem.js` 在 Webview 侧实现 `rz` / `sz` 协议:
- SSH 输出事件必须传 `Vec<u8>` JSON 字节数组,禁止先 `String::from_utf8_lossy`;ZMODEM 是二进制协议,一次 UTF-8 损失转换就会破坏握手和文件
- 前端所有 SSH 输出先经过 `Zmodem.Sentry`;普通终端字节由 `to_terminal` 交给 `TextDecoder(stream:true)` 与 xterm,ZMODEM 字节由 session 消费
- 协议回包通过 `ssh_write_binary(Vec<u8>)` 写入 russh channel;普通键盘输入仍走 `ssh_write(String)`
- 远端执行 `rz` 时弹出本地文件选择条并发送;远端执行 `sz <file>` 时接收后触发本地保存
- 后续若替换协议库,必须保留“端到端原始字节”边界并用真实 lrzsz 主机做双向回归

## 4. Sidecar 通信

- MVP 用 `stdio JSON-RPC`(Go `bufio.Scanner` 读 stdin)
- Rust 侧读写循环分离,按请求 ID 关联并发响应,单次 RPC 默认超时 120 秒
- 启动时必须完成协议版本与关键 RPC 能力握手,禁止加载旧 Sidecar
- 性能敏感场景升级到 `gRPC over Unix Socket`
- 协议版本号:Sidecar 启动时打印,便于排查

### 4.1 Sidecar 路径解析

`SidecarManager::start()` 通过 `std::env::current_exe()` 获取主程序 exe 路径,然后按优先级检查以下候选路径:

| 优先级 | 路径 | 场景 |
|---|---|---|
| 1 | `<exe_dir>/starhub-sidecar[.exe]` | 生产环境:sidecar 与主程序同目录 |
| 2 | `<exe_dir>/sidecar/starhub-sidecar[.exe]` | 生产环境:sidecar 子目录 |
| 3 | `<exe_dir>/../sidecar/bin/starhub-sidecar[.exe]` | 开发环境:主程序在 `src-tauri/target/<profile>/` |
| 4 | `<exe_dir>/../../sidecar/bin/starhub-sidecar[.exe]` | 开发环境备用 |
| 5 | `<exe_dir>/../../../sidecar/bin/starhub-sidecar[.exe]` | 开发环境:主程序在 `src-tauri/target/debug/` |

**开发时**:Windows 主程序位于 `src-tauri/target/debug/starhub.exe`,Unix 主程序为 `src-tauri/target/debug/starhub`;Sidecar 分别为 `sidecar/bin/starhub-sidecar.exe` 与 `sidecar/bin/starhub-sidecar`。

**打包时**:需确保 sidecar 二进制与主程序 exe 放在同一目录(或 `sidecar/` 子目录)。推荐配置 `tauri.conf.json`:

```json
{
  "bundle": {
    "externalBin": ["../sidecar/bin/starhub-sidecar"]
  }
}
```

> ⚠️ Go sidecar 编译时必须指定正确的 `GOOS` 和 `GOARCH`(如 `GOOS=windows GOARCH=amd64`),否则二进制无法在目标平台运行。

## 5. Tauri 2 跨平台打包

- macOS arm64 + x86_64 需双架构打包(用 `cargo tauri build --target universal-apple-darwin`)
- Windows 代码签名需 EV 证书(否则 SmartScreen 警告)
- Linux 固定 Ubuntu 24.04 / glibc 2.39 基线,使用原生 x86_64 与 ARM64 runner 分别构建,禁止跨架构生成 AppImage
- **截图栈(xcap → pipewire/libspa 0.10.1)要求系统 PipeWire/ spa 头 ≥ 1.0**:`libspa-sys` 的绑定是构建时用 bindgen 从系统 spa 头生成的,Ubuntu 22.04 的 0.3.48 头缺 `spa_video_info_raw.flags` 且 `spa_meta_region_is_valid`/`spa_meta_first` 还是宏(bindgen 无法导出成可调用函数),`libspa 0.10.1` 编译报 E0425/E0560/E0308 一串错误——这就是「Windows 用 WGC 后端不碰该链所以绿、GitHub Linux 必挂」的原因;Linux 构建基线因此定在 24.04,旧系统运行时由 `screenshot_begin_region` 预检 `pipewire --version` 提示升级到 Ubuntu 24.04+
- **截图栈 Linux 编译依赖(xcap 官方清单)**:`libpipewire-0.3-dev libspa-0.2-dev libgbm-dev libegl-dev libwayland-dev libxcb1-dev libxrandr-dev libdbus-1-dev`——`libgbm-dev` 缺失时链接期报 `rust-lld: unable to find library -lgbm`(Wayland 后端 libwayshot-xcap → Rust `gbm 0.18` FFI 直链)
- Linux 每个架构必须同时产出 AppImage、DEB、RPM;AppImage 内置 WebKitGTK/GTK 与静态 Go sidecar,DEB/RPM 由包管理器解析系统依赖
- `scripts/verify-linux-bundles.sh` 必须校验三类包、架构、sidecar 执行权限/静态链接、DEB/RPM 依赖和 `ldd` 的 `not found`;缺一项不得发布
- AppImage 面向主流 glibc 桌面发行版,不宣称兼容 Alpine(musl)或无 FHS 兼容层的 NixOS;无 FUSE 环境使用 `--appimage-extract-and-run`

## 6. 应用图标管理(重要)

> 换 Logo 时最容易踩的坑:改了打包图标但应用内 / 快捷方式还是旧的。

**图标存在 3 个独立位置,必须全部更新才不漏**:

| 位置 | 文件 | 作用 | 更新方式 |
|---|---|---|---|
| 打包图标 | `src-tauri/icons/icon.ico` / `icon.png` / `icon.icns` / 各尺寸 PNG | exe 图标、桌面快捷方式、任务栏、托盘 | `npx @tauri-apps/cli icon <源图.png>` 一键生成全套 |
| 应用内标题栏 | `src/assets/logo-star.png` + `CyberLayout.vue` 的 `.logo` | 自定义标题栏左上角 Logo(`decorations: false` 时系统标题栏不渲染,Logo 全靠前端画) | 替换图片 + 确认模板用 `<img :src>` 而非 CSS 几何图形 |
| 前端其他引用 | `src/assets/logo.png` 等 | 设置页、关于弹窗、Loading 等场景 | 全局搜索 `logo` 确认无遗漏 |

**换 Logo 标准流程**:

1. 准备一张 1024×1024 透明背景 PNG,放入 `icons/_candidates/`
2. 用 `npx @tauri-apps/cli icon icons/_candidates/xxx.png` 生成 `src-tauri/icons/` 全套(ICO/ICNS/PNG/iOS/Android/Store Logo)
3. 把生成的 `icon.png` 复制到 `src/assets/logo-star.png`(标题栏用)
4. 确认 `CyberLayout.vue` 模板中 `.logo` 用 `<img :src="logoUrl">`,不是 CSS 画的几何图形
5. 全局搜索 `logo.png` / `icon.svg` / `logo-mark` / `logo-core` 确认无残留旧引用
6. **清 Tauri 构建缓存**:`cargo clean -p starhub`(否则 exe 里嵌的还是旧图标)
7. 重新 `npm run tauri build`

**踩过的坑(v0.13.2 ~ v0.13.5)**:

- ❌ 源图是 JPEG 伪装成 .png → `tauri icon` 生成的图标无透明通道,exe 显示为带米黄背景的方形
  - 修复:用 .NET `System.Drawing` 转真 PNG + `LockBits` 把背景色设为 Alpha=0
- ❌ 标题栏 Logo 用 CSS 画的 `S` 轨道几何图形(`.logo-mark` / `.logo-orbit` / `.logo-core`),换 Logo 后应用内不变
  - 修复:CyberLayout 模板改为 `<img :src="logoUrl">`,删除 CSS 几何 Logo 样式
- ❌ 改了 `icon.ico` 但 exe / 快捷方式还是旧图标 → Tauri 构建缓存(`target/`)里嵌的旧图标
  - 修复:`cargo clean -p starhub` 后重新打包
- ❌ `icon.svg` / `icon-source.svg` 仍是旧设计 → `tauri icon` 不生成 SVG,需要手动用 `icon.png` base64 嵌入 SVG `<image>`
- ❌ Windows 安装后桌面快捷方式图标不更新 → Windows 图标缓存问题
  - 修复:`ie4uinit.exe -show` 或重启资源管理器

## 7. Univer 视图下方留白与 CSS 类名冲突

> **⚠️ 已废弃** (2026-08-26): StarHub 的 Excel 前端已不再使用 Univer 渲染(改用 CodeMirror + 后端 Go excelize 直写 xlsx),`vendor/univer` / `vendor/univer-presets` 两个 submodule 已移除。以下内容仅作历史踩坑记录保留,不再适用于当前代码。
>
> v0.14.6 ~ v0.14.14 曾连续从尾行数量、canvas resize、grid 模板和 flex 高度链排查 Excel 下方留白,最终在 v0.14.15 通过 Vite 真实 DOM 尺寸测量找到根因。后续 Agent 遇到类似问题必须先量尺寸,不要继续凭视觉猜高度。

**最终根因**:

- StarHub 原本把 Univer 挂载容器命名为 `.univer-grid`
- Univer 0.25.1 自己也提供全局 Tailwind 工具类 `.univer-grid { display: grid }`
- 全局样式污染挂载容器后,504px 高度被浏览器自动拆成约 `290px + 214px` 两个 grid 行
- `[data-u-comp="workbench-layout"]` 只占第一行,第二行就是截图中的整块留白;因此继续给 Workbench 内部补 `height:100%` / `flex:1` 无法解决外层分行

**修复与硬约束**:

1. Univer 挂载根必须包含 `.univer-host`(数据库结果可同时带 `.db-univer-host`),禁止改回 `.univer-grid`
2. 新增第三方组件挂载类时,必须先检查其编译 CSS 中是否存在同名全局工具类
3. 留白问题先在 Vite dev server 注入可重复 mock 数据,同时测试默认窗口与用户截图尺寸
4. 用 `getBoundingClientRect()` + `getComputedStyle()` 从外向内记录:
   - StarHub shell
   - 挂载根
   - `[data-u-comp="workbench-layout"]`
   - `[data-range-selector]`
   - 数据 canvas
5. 正确状态是挂载根与 Workbench 等高、`data-range-selector` 与数据 canvas 等高;若父层已被拆行,不要先改 canvas resize
6. 修复后必须在浏览器截图确认网格连续铺到 Sheet 标签栏,并检查控制台无新增错误
7. 覆盖 Univer 内部布局时必须限制到直接子级(例如 `> section > .univer-grid`),禁止用后代选择器覆盖全部 `.univer-grid`;后者会误伤 Ribbon 内部网格并把工具按钮折叠成省略号
8. Sheet 切换禁止 dispose/recreate Univer。工作簿首次加载后只调用 `workbook.setActiveSheet()`,仅在缓存对象真正替换时用 `setValues()` 原地同步数据
9. 数据库分页、排序、刷新和保存后也必须保留 `DbUniverGrid` 实例,用 loading 遮罩 + 原地 `setValues()` 更新,否则会闪白并丢失滚动位置

**本次实测判据(v0.14.15)**:

- 修复前:`.univer-grid` 挂载根 `display:grid`,`grid-template-rows: 290px 214px`,Workbench 高 290px
- 修复后:`.univer-host` 挂载根 `display:block`,挂载根与 Workbench 均高 504px,数据 canvas 与 `[data-range-selector]` 均高 399px

## 8. SFTP Subsystem 路径错误与受控降级

- `russh` 的 `request_subsystem(true, "sftp")` / `exec(true, ...)` 只负责发送 channel request；必须继续读取 channel 的 `Success` / `Failure`，否则服务端拒绝会被后续 `russh-sftp` 初始化误判成 Timeout。
- 建链期间必须区分 stdout 的 SFTP 二进制协议与 `ExtendedData` stderr，并完整保留 exit status、exit signal、request failure 和提前关闭状态。面向用户的错误不得只显示 `[SFTP_FAILED]` 或 Timeout。
- 默认 `sftpLaunchMode=auto`：先使用标准 subsystem，确认是可恢复的服务端启动失败后才执行固定探测脚本；找到可执行 `sftp-server` 才用 SSH exec 降级。真实网络超时、SSH 通道打开失败等错误不自动重试为 exec。
- `subsystem` 模式用于严格禁止降级；`custom` 模式只接受远端 Unix 绝对路径，后端必须再次做长度、控制字符校验和 POSIX 安全引用，禁止接收任意命令文本。
- 自动探测失败时要同时展示 subsystem 原始错误与探测结果，并建议服务端优先改为 `Subsystem sftp internal-sftp`、执行 `sshd -t` 校验后 reload sshd。

## 9. AI 多轮上下文与会话绑定

- Planner 必须接收有界的历史对话,不能只发送当前输入;重试和结构化选项重新规划时要移除一次重复的当前请求。
- 顺序 Executor 必须注入已经完成的前置步骤结果;同一并行批次不得读取仍在执行的兄弟步骤结果。
- `runAgent` 必须在追加流式 assistant UI 占位前复制消息快照,禁止把空 assistant 发送给 Provider。
- 正式 tab 会话只持久化有界的用户/助手文本,不得把工具参数、工具原始输出、执行计划或 `#` 工具绑定写入 localStorage;恢复后工具范围为空。
- `#` 上下文在当前对话内沿用并持续可见,模块引用必须在绑定时固化为具体资产 ID,不得因后来新增资产扩大范围;清除按钮、新对话和应用重启都撤销绑定,写操作与高危动作继续逐次确认。
- AI 消息滚动位置由 keep-alive 页面实例在停用时捕获、激活后恢复;原本停留在底部的会话继续跟随新增内容,用户正在回看历史时不得强制跳到底部。
- 全局 AI 的 SSH 工具只能使用 exec-only 连接,禁止申请 PTY 或启动远端 shell;手动 SSH 标签页继续使用交互式 PTY,两条路径不得混用。

## 10. Windows 上 `dragDropEnabled` 与 HTML5 DnD 冲突(重要)

- `tauri.conf.json` 的 `dragDropEnabled: true` 是 SFTP / Excel 拖 OS 文件进窗口(`getCurrentWebview().onDragDropEvent`,拿完整路径)的前提,不能关。
- 但 Tauri 官方文档明确:**Windows 上开启它会拦截 HTML5 drag-and-drop**,`draggable` + `dragstart` / `dragover` 全部失效(macOS / Linux 不受影响)。
- 因此窗口内的"拖动手势"(如标签页拖出独立窗口)必须用 **Pointer Events + `setPointerCapture`** 自实现,禁止回到 HTML5 DnD;capture 还能保证拖出窗口外持续收到 move/up。
- 注意 pointer capture 会把拖拽后的 `click` 派发到源元素,需要一次性屏蔽(`suppressNextTabClick`)。**禁止用定时器屏蔽**(click 派发被事件循环延迟时定时器会先失效);要用 window capture 阶段的一次性 click 吞听器,并以 `pointerdown` once 监听兜底撤掉,避免误吞正常点击。

## 11. 标签页拖出独立窗口白屏(v0.32.6)

- 版本:v0.32.5 及之前
- 现象:把标签页拖出为独立窗口后,新窗口只有纯色背景,看不到标题栏和工作区内容(用户描述为"白屏")
- 根因(双重):
  1. `src/lib/windowDetach.ts` 的 `buildDetachedUrl` 生成 `index.html?detach=1&route=...`。Tauri WebviewWindow 加载后,`createWebHistory()` 拿到的初始 path 是 `/index.html`,而路由表只有 `/` 及其子路由,`/index.html` 不匹配任何路由,根 `<router-view/>` 渲染为空,CyberLayout 根本不会挂载。
  2. 即便把 URL 改成 `/`,`src/components/layout/CyberLayout.vue` 在独立窗口分支里调用 `assetStore.fetchAssets()` 时没有 `await`;`router.replace(detachedInfo.route)` 会抢在资产列表返回之前挂载 SshTerminal / DbView / DockerView 等组件。这些组件在 `onMounted` 里发现 `asset` 为空,会执行"资产已被删除 → 关闭 tab 并 `router.push('/')`"的兜底逻辑,把工作区推回空白占位页。
- 修复方案:
  1. `buildDetachedUrl` 返回 `/?${params.toString()}`,让新窗口初始 path 就是 `/`,与主窗口一致,CyberLayout 能正常挂载。
  2. 独立窗口 `onMounted` 里 `await assetStore.fetchAssets()` 完成后再 `router.replace(detachedInfo.route)`,确保工作区组件挂载时资产已就绪。
- 后续硬约束:
  1. 任何通过 `new WebviewWindow` 打开同应用页面的 URL 都必须用 `/` 或 `/path` 形式,禁止再传 `index.html` 给 vue-router 的 `createWebHistory`。
  2. 独立窗口的精简初始化若依赖 store 数据,必须等待数据就绪再让 `<router-view/>` 渲染依赖该数据的组件;否则要在组件内部识别 detached 模式并跳过"缺失即关闭"兜底。
  3. 新增类似"用 query 参数做窗口间协议"的功能时,先用浏览器打开 `/?key=value` 验证路由能匹配到目标组件,再进 Tauri 真窗口验证。

## 12. `v-show` 对多根节点组件静默失效(v0.39.1)

- 版本:v0.39.0(提交 75aee46 引入)
- 现象:DbDashboard 指标卡按 概览/性能/网络 tab 分组,点击「性能」「网络」tab 高亮变了但卡片网格毫无变化,用户感知为"没有内容"。
- 根因:`DashboardCard.vue` 是双根节点组件(`<button>` + `<v-dialog>` 并列,渲染为 Fragment)。Vue 3 的 `v-show` 作用于 Fragment 根组件时完全不生效,dev 下只打一条 `[Vue warn]: Runtime directive used on component with non-element root node`,display 永远不切换。
- 修复:把 `v-show` 从卡片组件上移到普通 `<div class="dashboard-grid">` 容器,每个 dbType 块内按 tab 拆 2~3 个容器;不能用 `v-if` 替代(切 tab 会销毁卡片,丢失 `sampledHistory` 趋势采样)。
- 后续硬约束:
  1. 给组件加 `v-show` 前先确认它是单根;多根组件(尤其是含 teleport/v-dialog 并列根的)一律把显隐控制放到外层原生元素上。
  2. dev console 出现 "Runtime directive used on component with non-element root node" 警告必须当 bug 处理,不能跳过。

## 14. rustls 双 CryptoProvider 导致 `ClientConfig::builder()` panic(v0.46.9)

- 现象: 「服务器网页访问」打开 HTTPS 站点(如 www.baidu.com)时,iframe 报 Chromium 错误页「127.0.0.1 未发送任何数据」(ERR_EMPTY_RESPONSE);HTTP(80 端口)站点正常。

  1. 只要依赖树里 rustls 0.23 同时带 `ring` 与 `aws-lc-rs`(Cargo.lock 的 rustls 条目 dependencies 里两个都出现),任何 `ClientConfig::builder()` / `ServerConfig::builder()` 调用点都必须改为 `builder_with_provider` 显式指定。

## 15. SSH AI 多行命令「prompt 返回超时」与 keep-alive 滚动锚点被离屏 DOM 清零(v0.47.2)

- 现象 A:AI 在 SSH 终端执行多行命令(如 `for n in ...; do tail -3 ...; done`),命令秒回,却等满 60s 报「等待 shell prompt 返回超时,已发送 Ctrl+C 恢复终端」。

- 现象 B:AI 助手(AiView)/ SSH 内嵌 StarAI 面板切换标签页后回到对话开头。
- 根因 B:Vue keep-alive 失活时**先把 DOM 移入离屏容器,再触发 deactivated 钩子**(runtime-core `deactivate`:先 `move` 后 `invokeArrayFns(instance.da)`);离屏元素 scrollTop 读数为 0,`onDeactivated` 里的 capture 用 0 覆盖了 `@scroll` 记录的正确锚点,激活后恢复到顶部。
- 修复 B:`onDeactivated` 里先判 `container.isConnected`,已离屏就保留 `@scroll` 记录的最后锚点;AiChat 补齐同样的锚点保存/恢复;恢复改为「同步一次 + rAF 校正一次」双保险(后台窗口 rAF 可能不触发)。
- 后续硬约束:

## 16. 网页访问 iframe 报「127.0.0.1 拒绝连接」实为 X-Frame-Options / CSP frame-ancestors 拦截(v0.47.4)

- 现象: 「服务器网页访问」打开 www.baidu.com,iframe 只显示一个红色禁止图标(Chromium 子帧错误页),主帧打开的错误文案是「127.0.0.1 拒绝连接 / refused to connect」。同一时刻 `curl` 直连网关端口却完全正常(200 + 改写后 HTML,SSH 隧道链路通畅)。
- 根因: 这**不是** TCP 层的 `ERR_CONNECTION_REFUSED`,而是 `ERR_BLOCKED_BY_RESPONSE`——网关把上游站点的 `Content-Security-Policy: frame-ancestors 'self' ...`(以及部分站点的 `X-Frame-Options`)原样透传给 webview,`frame-ancestors` 白名单里没有 `127.0.0.1`,Chromium 拒绝把响应渲染进 iframe。其错误页文案恰好是「<host> 拒绝连接」,与端口失效的表现一模一样,导致此前数版修复都在排查监听端口存活 / accept 循环,方向全错。
- 排查手段(可复用):
  1. `netstat -ano | findstr LISTENING` 按 starhub.exe 的 PID 确认网关端口确实在监听;
  2. `curl -D - "http://127.0.0.1:<port>/__proxy__/https/<host>/"` 绕过 webview 直验网关全链路(curl 不执行 XFO/CSP,能通就说明 TCP/SSH/TLS 都没问题);
  3. 审计库 `%APPDATA%/com.starhub.app/starhub.db` 的 `audit_log` 表 `web_access` 记录里有 `gatewayPort`,可核对前端实际使用的端口(注意 WAL 未 checkpoint,要连 `-wal` 一起拷)。
- 修复方案: `src-tauri/src/ssh/web_gateway.rs` 回写响应时统一经 `should_skip_response_header` 过滤,剥离 `x-frame-options` / `content-security-policy` / `content-security-policy-report-only`(整个 CSP 一并剥离:改写后的页面经 127.0.0.1 源加载,上游 CSP 的 script-src / img-src 等指令同样会拦截改写产物);新增单测与端到端断言(百度实测会发 frame-ancestors);网关启动、上游失败、上游超时补 `tracing` 日志。
- 后续硬约束:
  1. 再遇「127.0.0.1 拒绝连接」先分清 `ERR_CONNECTION_REFUSED`(端口没人听)与 `ERR_BLOCKED_BY_RESPONSE`(XFO/CSP 拦截嵌入):curl 能通而 iframe 不通,必是后者,直接去查响应头。
  2. 网关/代理类转发上游响应头时,嵌入拦截类头(XFO、CSP、CSP-Report-Only)默认剥离;调整透传头清单时同步更新 `should_skip_response_header` 的单测。

## 26. .bat 文件里的 UTF-8 中文注释会炸 cmd 解析(v0.79.0)

- **症状**:`npm run cargo:check/test`(走 `scripts/cargo-env.bat`)偶发执行"乱码片段",报 `'×' 不是内部或外部命令` 之类,或静默串行执行被搅碎的注释内容;从 Git Bash 直接调 cargo 则正常。

- **升级后 UI「看起来没变」的排查顺序**(本节为实弹演练结论):① 看磁盘唯一 dist:`resource_dir/dsh-runtime/node_modules/@deepseek-ai/dsh-web-frontend/dist/assets/index-*.js`,物理 grep 特征串(如双栏表头文案)确认新代码在包里;② 对运行中的实例直接 `GET /` 并拉取入口 JS 核对同一特征(注意 Invoke-WebRequest 的 `.Content.Length` 是字符数不是字节数,与文件字节比对会差多字节字符量);③ `netstat -ano` 找监听端口的 OwningProcess 启动时间,确认进程树确实换血过;④ `%APPDATA%\com.starhub.app\dsh-web-home-<N>` 是端口冲突遗留的化石目录(N≠当前监听端口即非活跃),活跃 home 的判据是 `sessions/` 正在实时写盘,别被 N 个并存目录骗去查错树;⑤ 外部浏览器无痕窗口对照可秒级排除客户端缓存因素;⑥ 最后才是清 WebView2 持久缓存(`EBWebView\Default\Cache` + `Code Cache`,保留 Local Storage 不丢设置)。dsh webserver 的静态响应不带 Cache-Control/ETag,WebView2 违规复用旧资源是真实存在的坑。

- **工具卡文件链接的悬空陷阱**:卡片上的文件名可点击,点击走 `local_read_text_file`(src-tauri/commands/local.rs L345 起)读实时元数据与正文;若目标文件已被删除(AI 当场建的临时验证文件清理后就中招),错误以裸 OS 文案直达 UI:`read metadata failed: 系统找不到指定的文件。 (os error 2)`。后续版本应把该错误降级为友好提示(如「文件已不存在」),并在 diff 卡层面对悬空路径给出状态标记。

## 29. Rust ↔ sidecar 参数键名漂移:docker_exec 静默坏了一个版本段(v0.105.0)

- **症状**:`docker_exec` 域工具自「方案1:域工具迁 Rust 进程内执行」后实际一直失败,但无用户报告——直到沙箱桌面 M1 复用 `docker.exec` 时逐字段核对 sidecar handler 契约才发现。
- **根因**:`harness/domain.rs` 的 `execute_docker` 发 `{"container", "cmd"}`,而 sidecar `adapters/docker.go` 的 handler 结构体是 `containerId`/`command`(json tag)。两侧各自能编译、各自有测试,但**键名契约没有任何一处共享定义**,漂移零告警。
- **修复**:对齐为 `containerId`/`command`;沙箱桌面模块建立新约定——**新增 sidecar 调用前先读 handler 的 struct json tag,不复读调用方既有代码**。
- **后续硬约束**:Rust 与 Go 之间的 RPC 参数契约以 sidecar handler struct 为唯一事实来源;给 sidecar 加新方法时,在 `handlers.go` 注册处顺手核对一遍既有调用方的键名。

## 30. sidecar RPC 120 秒默认超时截杀长耗时操作(v0.105.1)

- **症状**:AI 首次执行 `desktop_build_template` 报「Sidecar RPC timed out after 120 seconds」;镜像构建在 daemon 侧仍在继续,但工具调用已失败。
- **根因**:`SidecarManager::call` 固定 `DEFAULT_RPC_TIMEOUT = 120s`;镜像构建(5-15 分钟)、大层 commit、长 timeoutSec 的 docker exec 全部超过它。设计文档写了构建时长,落地时没核对这条链路的超时上限。
- **修复**:`call_with_timeout` 提为 pub,desktop 模块新增 `platform_call_with_timeout`——buildImage 1800s / commitContainer 600s / docker exec 跟随 timeoutSec+30s;超时不再硬失败,降级为落盘 Dockerfile + 返回手工 `docker build`/`docker commit` 命令指引(用户执行后重调即命中 daemon 层缓存)。
- **后续硬约束**:凡新增「可能超过 2 分钟」的 sidecar RPC,必须显式传超时,并在设计文档里写清该操作的最坏耗时;超时文案一律带人工降级路径(可手工执行的命令),不只报错。
- **旁证**:dsh 侧链路无隐藏超时——timeout-policy 只在工具声明 timeoutMs 时生效(bridged 工具未声明即无限),sdk-protocol transport.request 无默认超时,前端转发路径的 TOOL_EXEC_TIMEOUT=180s 只管 dsh://tool-exec(desktop_* 进程内执行不经此路)。

## 31. profiles/node_modules junction 钉死旧路径:升级后加载陈旧/开发树插件代码(v0.106.0)

- **症状**:用户安装了 v0.106.0 包(exe ProductVersion 与打包 runtime 均为新版),但 GUI 仍是旧版界面;`GET /plugins/@deepseek-ai/dsh-starhub-client-nav/client.js` 返回旧 bundle。
- **根因**:`web.rs` 物化 `$DSH_HOME/profiles/node_modules` 的本地包 junction 时是「`link.exists()` 则复用」——junction 目标在创建时钉死当时解析的 runtime 路径,之后永不校验。dev 与 release 共用同一 `%APPDATA%\com.starhub.app`(Tauri identifier 相同),dev 期建的 junction 指向 `vendor/deepseek-harness/packages/starhub/<pkg>`(源树,lib/ 被 gitignore 常过期),release 升级后继续经它加载旧 lib;同理安装目录变更(E:\StarHub1 → 别处)也会让 junction 指向化石路径。
- **修复**:`web.rs` 新增 `ensure_dir_link_fresh`:已存在的链接用 `symlink_metadata` + `read_link` + 双侧 `canonicalize` 校验指向,漂移/悬挂即删旧重建(junction 用 rmdir、Unix symlink 用 unlink);位置被真实目录占用时告警跳过,绝不删用户数据。LOCAL_PACKAGES 与 RUNTIME_HOSTED_PATCH_DEPS 两处循环统一走它,附 5 分支回归测试。
- **后续硬约束**:
  1. 任何「指向随版本/安装位置漂移的目标」的链接/缓存,建立时必须先校验既有指向,「存在即复用」只适用于目标恒定的场景;
  2. 判断链接是否存在用 `symlink_metadata`,不要用 `Path::exists()`——后者跟随链接,悬挂 junction 返回 false,mklink 又因「已存在」失败,永远卡死;
  3. Windows 上给 `mklink /J` 传参(经 Rust `Command`)必须用原生分隔符的分段 `Path::join`,整串含 `/` 的路径会让 cmd 内建解析失败(exit 1,无 stderr)。

## 32. 审批 never 策略短路 hard 确认:全访问下 desktop_exec 必拒(v0.106.0)

- **症状**:权限预设为 danger-full-access(全访问)时,`desktop_exec` 等恒确认(hard 档)工具调用直接报「the user rejected tool」,确认卡根本不弹;系统提示里出现 "Approval prompts are disabled in this session"。
- **根因**:两层策略互相矛盾。StarHub 风险门(approval-bridge)的设计意图是「hard 档删除/高危确认与预设脱钩,never 下也弹卡」,门也确实对 hard 返回了 `ask`;但 `dsh-user-approval` 服务的 `decide()` 在会话策略为 never 时**先于所有 answerer 直接 return "rejected"**,确认卡应答器永远收不到请求。approval-bridge 在 session/created 把 danger-full-access 映射为 never,正好踩进这个短路。
- **修复**(v0.106.1,两处协同,均不动 dsh 内核):① approval-bridge 任何 preset 都钉 `ask`,「全访问放行软确认」改由风险门按 preset 判定(折叠会话 `permission/preset` 事件,缺省读 settings.yaml 的 defaultPreset)——全访问 = 只有 hard 档(DELETE FROM/rm -rf/desktop_exec 等)弹确认,其余静默;② `examples/starhub-web/cordis.patch.yml` 覆盖 permission-presets 的 presets 表,danger-full-access 的 approval 由 never 改 ask(否则 /permission 切换又经 permission-presets 把 never 写回)。已在 never 卡住的老会话:重新切一次 preset(或新开会话)即恢复。
- **后续硬约束**:
  1. 给 dsh 审批体系接新档位时,确认卡的可达性要以「answerer 真的收到 approval/request」为验收点,不能只看风险门返回了 ask;
  2. StarHub 组合里禁止再把任何 preset 映射为 approval never;约束注记在 starhub-web patch 的 permission 行注释里(DSH_PERMISSION_MODE=danger-full-access 的 env 组合会派生 custom fail loud,勿设置)。

## 34. 沙箱桌面跑 GUI Linux 应用(微信为例):apt 受限、运行时依赖、中文输入与点击命中(v0.106.x)

- **背景**:在沙箱桌面(Ubuntu 24.04 / Xvfb / xfce)里跑微信官方 Linux 版(WeChat 4.1.1),验证 AI 用 `desktop_*` 工具操作真实 GUI 应用(扫码登录、选会话、发消息)的可行性。结论:可行,但依赖与交互各有硬坑。
- **安装链路(apt 在沙箱内不可用)**:受限容器里 `setegid/seteuid` 被禁、`/var/cache/apt/archives/partial` 不可写,`apt-get`/`apt-get download` 全挂(报 `E: Sub-process http returned an error code (112)`,配置阶段 `libxkbcommon-x11-0` 也因依赖不满足卡住)。**改用 `curl` 直接下载 .deb + `dpkg -i`(必要时 `--force-depends`)可正常落地**,`ldconfig` 后生效。给 apt 让缓存目录到 `/tmp`(`-o Dir::Cache::Archives=/tmp/x`)也解决不了 http 子进程降权问题。
- **运行时依赖(微信 deb 只声明 fonts-noto-cjk,实际缺一批,逐个 `ldd` 补齐)**:
  - `libatomic1`、`libxkbcommon-x11-0`、`libxcb-xkb1` / `libxcb-icccm4` / `libxcb-image0` / `libxcb-shape0` / `libxcb-render-util0` / `libxcb-keysyms1`(xcb 系列源在 `pool/main/x/xcb-util-*`,noble 版本带 `-buildN` 后缀)、`libnss3`+`libnspr4`、`libasound2t64`;

  - `fonts-noto-cjk`:缺了中文渲染成乱码(登录页标题变成「送拉S崩吧」),装完 `fc-cache -f` 生效。
- **中文输入**:`xdotool type '中文'` 报 `Invalid multi-byte sequence`(`xdo_enter_text_window` 只认当前键位,不支持 CJK)。**用 `printf '...' | xclip -selection clipboard` + `xdotool key ctrl+v` 粘贴**即可(基础镜像无 xclip/xsel,需先装 xclip)。
- **GUI 自绘按钮点击不生效**:`desktop_click` 点「Send(S)」发送按钮多次不触发,改为**聚焦输入框后按回车**(`desktop_press_key Return`)发送成功。对这种自绘按钮,回车命中比像素级点击更可靠;按钮上的 `(S)` 即 Send 的快捷键提示。
- **坐标换算**:`desktop_screenshot` 落盘是 1920×1080,但 `read_image` 给模型的是缩小到 1066×600 的图——读图估点后要 **×1.8** 换算成物理像素再 `desktop_click`,否则点偏到桌面空白(表现为「点了没反应」)。

## 35. Android 实体机 adb 通道:exec-out CRLF、input text 转义、scrcpy 协议钉版本(v0.107.0)

- **背景**:Android 实体机直连(设计 `docs/superpowers/specs/2026-08-30-android-device-design.md`)落地时按 scrcpy/ADBKeyBoard 源码与实测确认的一组 adb 交互坑,全部固化进 `src-tauri/src/android/mod.rs` 纯函数与单测。
- **exec-out CRLF 二进制损坏(adb < 1.0.41,Windows)**:`adb exec-out screencap -p` 在旧版 Windows adb 上把每个 `\n` 改写为 `\r\n`(原有 `\r\n` 变 `\r\r\n`),PNG 流损坏。**修复方向是「k 个 \r + \n → k-1 个 \r + \n」,不是无脑删 \r**——PNG 8 字节 magic 自身就含合法 `\r\n\x1a\n`(初版修复把合法 CRLF 也删掉,单测抓住);magic 恰好是现成探针:先验 magic,不过再修复重验,仍不过报「升级 platform-tools」。初版只验前 4 字节 `\x89PNG` 也抓不到损坏(损坏流前 4 字节不变),必须验全 8 字节。
- **`input text` 双层转义**:`%` 是 input 命令的格式符(字面量 `%%`、空格 `%s`),先做这层转义,**再**套 shell 单引号(`sh_quote`,内部 `'`→`'\''`)防 toybox sh 展开;只支持 ASCII 可打印,非 ASCII(中文)走 ADBKeyBoard 广播(`am broadcast -a ADB_INPUT_TEXT --es msg`,需 `pm path com.android.adbkeyboard` 探测,未装给安装引导,不静默失败)。
- **unauthorized / offline 状态**:`adb devices` 状态非 `device` 时一切操作报「error: device unauthorized」——`android_connect` 探测状态并直接引导「请在手机上点『允许 USB 调试』」,`android_list_devices` 输出逐台标注。
- **scrcpy-server 协议与版本钉死**:server 首参必须等于自身版本号(`SCRCPY_SERVER_VERSION` 与 bundled jar 同步,不匹配即退出);`tunnel_forward=true` 时视频 socket 布局 = 1 哑字节 + 64B 设备名 + 12B codec meta + 帧(12B 元头:u64 BE pts+flags,bit63=config、bit62=keyframe,u32 BE size);版本升级必须按对应版本 `Options.java` 复核参数键名与协议(`resources/scrcpy/PROVENANCE.md` 记录了升级步骤)。下载二进制一律用官方 release 的 `SHA256SUMS.txt` 校验(v0.107.0 曾因 `Invoke-WebRequest .Content` 返回字节数组导致哈希比对脚本假死,改用 `curl.exe` 拉文本比对)。
- **control=false 的取舍**:无控制通道 ⇒ 无法请求关键帧,客户端从环形缓冲最近关键帧重同步,开播/丢帧后黑屏 ≤ 一个 GOP(12fps × 默认 GOP 约数秒);接管输入一律走 `adb shell input`(mpsc 入泵),不经 scrcpy。
- **adb forward 端口 TOCTOU**:`bind 127.0.0.1:0` 抢号后释放再 `adb forward`,窗口内有竞争;同一 serial 的 scrcpy 会话由注册表去重,旧窗口销毁时 best-effort `adb forward --remove`。
- **直播页坐标映射**:一律「显示矩形 → 设备物理像素」(`meta.width/height` = `wm size` 物理分辨率),与视频是否被 max_size 缩放无关;旋转后页面按新帧自然重排,历史坐标作废,需重新截图估点。

## 36. Android 截图坐标「点偏 1.3 倍」:模型看到的是缩略图,不是落盘原图(v0.108.0)

- **现象**:AI 连点多次都落在目标左上方(如搜索图标在物理 (995,215),连点 (715,147)/(745,148) 全空),自查对话才发现换算关系来回搞反。
- **根因**:`android_screenshot` 落盘是设备物理分辨率 PNG(如 1200x2670),但模型经 `read_image` 看到的是 harness 缩小后的图(920x2047)——缩小提示「multiply coordinates by 1.30」是给「读图」用的,而 `android_tap` 描述只写「物理像素」,两条提示词之间没有任何一座桥,模型只能自己悟。这不是坐标映射 bug(`input tap` 直吃物理像素,回放帧核对无误),是**工具契约文本缺一环**。
- **修复**(三处协同):① `capture_screenshot` 直读 PNG IHDR 返回当次真实宽高——**不信任 connect 时缓存的 `wm size`**(横竖屏切换/`wm size` 被改都免疫,任意机型不写死);② `android_screenshot` 结果文本注明分辨率并写明「坐标 = 截图原始文件像素;read_image 注明 multiply coordinates by k 时先把图上坐标乘 k」;③ tools 插件里 tap/double_tap/swipe/scroll 描述同步写明换算规则。

## 37. 坏插件导致 dsh web / runtime 启动超时无法恢复:坏插件自救自动禁用(v0.113.1)

**现象**:装入并启用某个 `dsh` 插件(如 `dsh-status-rotator`)后,重启 StarHub 时卡在 dsh web / runtime 启动,约 60s 后报「就绪探测超时/initialize 失败」;而且插件一直处于 `enabled`,每次重启都死在同一处,连设置页都进不去(网页从未起来)。

**根因**:dsh 组合的 boot() 会跑 `assertEntriesActivated`,任何一条 entry 激活失败(常见于用户插件的 **node 半 `apply()` 抛错**)都会让整个组合 `fail-loud`——`installFailLoud` 写 stderr 后 `process.exit(1)`。StarHub 侧:
- `web.rs::spawn` 只轮询 `GET /` 等 200,进程退出后永不 200,耗满 `READY_TIMEOUT`(60s)才 `kill` 并报 `ReadyTimeout`;
- `HarnessManager::initialize` 的 `runtime.call("initialize")` 在进程退出后 RPC 超时/断开。

插件仍留在 `registry.json`(enabled=true),下次重启 `sync_user_client_plugins` / `prepare_runtime_config` 又把它加回组合 → 死循环。B-4 已把「坏插件自救」列为 TODO,但首版只做了手动引导(去设置页禁用),而 web 起不来时设置页不可达。

**修复**(坏插件自救,B-4 TODO 落地):
- `plugins.rs` 新增 `disable_user_plugins`:禁用全部**非内置且已启用**的用户插件(保留目录与 registry),写回 registry.json + 重写 entries yml,返回被禁用列表,幂等。
- `web.rs::spawn` 就绪探测**提前感知子进程退出**(`child.try_wait()`),不再空等满 60s;超时/退出时自动禁用用户插件并 `spawn_once` 重试一次。
- `mod.rs::HarnessManager::initialize` 失败时同策略:禁用用户插件 → 弃掉损坏 runtime → 清空指纹 → 强制重 spawn。

**效果**:任何(node 半)有问题的插件不再阻塞启动;重试成功后应用回到可用状态,插件在设置页显示为已禁用、可重新启用(重新启用前可先手动排查)。坏插件目录与 registry 记录保留,不删除用户数据。

**后续硬约束**:
- 用户插件的 node 半必须能安全激活(`apply()` 不抛错);不确定时插件自身应 try/catch,或把非要 webServer/settings 的逻辑做成**轮询等待**(参照 status-rotator 的 `setInterval` + `attempts>=20` 清定时器)而非同步抛错。
- StarHub 侧新增启动失败自动禁用是「最后一道保险」,依赖 dsh 进程在 boot 阶段退出;若插件在**运行中**抛 UnhandledRejection,仍由 `installFailLoud` 兜底退出,同样会触发本自救。
- 若某插件总是导致超时而自救也失败(非插件问题,如闭包缺失),错误仍会透传,定位看 tracing 的 stderr(drain_lines 已转发)。

## 39. patch 追加粘连致 YAML 失败:UI 插件「装了但用不了」实为启动误禁(v0.114.1)

**现象**:用户安装了 `dsh-status-rotator` 之类的 `dsh.client` UI 插件并启用,但一直「用不了」——重启/重进后插件列表里它仍显示已启用,可效果不生效;或更隐晦:设置页显示它已被「坏插件自救」自动禁用,重新启用后又被打回禁用,反复死循环。

**根因**(v0.114.1 定位,与 §37「坏插件自救」是**同一个症状、两个不同原因**):
- `web.rs::rewrite_patch_port` 用 `template.lines().collect::<Vec<_>>().join("\n")` 重写 `cordis.patch.yml`。Rust 的 `str::lines()` 会**吞掉末行换行**(末尾 `\n` 不产生一个空行),因此改写后的字符串不再以 `\n` 结尾;
- `web.rs::sync_user_client_plugins` 随后用 `patch.push_str("    - id: '...'\n      name: '...'\n")` 在末尾追加用户插件的 entry 行。由于字符串已无尾换行,首个 `- id:` 与上一行(通常是 `commit-message` 的 `timeoutMs: 30000`)**直接粘连**,变成:
  ```
  timeoutMs: 30000    - id: 'dsh-status-rotator'
        name: 'dsh-status-rotator'
  ```
- 这是一个**非法 YAML**(mapping entry 缩进错误)。dsh web 组合 boot 时 `parsePatchList` 抛 `YAMLException: bad indentation of a mapping entry`(日志 `dsh web stderr` 可见),整个进程退出 → 就绪探测 60s 超时 → **触发 §37 的坏插件自救**,把 `dsh-status-rotator` 等所有启用的用户插件误禁;
- 用户在插件页重新启用 → 下次 spawn 又粘连 → 又被误禁 → 外观就是「插件装了但一直用不了」。

**修复**(v0.114.1):
1. `rewrite_patch_port` 在模板以换行结束时补回末行换行(`template.ends_with('\n') && !out.ends_with('\n')` → `out.push('\n')`);
2. `sync_user_client_plugins` 追加前强制保证 patch 以换行开头(`if !patch.is_empty() && !patch.ends_with('\n') { patch.push('\n'); }`)——防御任何未尾换行的输入,绝不破坏 yml 结构;
3. 补回归单测 `rewrite_patch_preserves_trailing_newline_for_append`,覆盖「模板有尾换行 + 无尾换行」两种输入。

**后续硬约束**:
- 凡是「读模板 → 字符串拼接修改 → 再写回」的 YAML/文本管线,拼接/追加前要保证边界是完整的换行;`str::lines()` 吞尾换行是经典坑,拼接类操作后跑一次 `serde_yaml`(或直接让目标解析器 parse)做自检最稳。
- §37 的「坏插件自救」是**最后一道保险**,不是诊断工具。任何「启用了插件但启动失败」的排查顺序应是:① 看 `dsh web stderr` 的 YAML/加载异常 → ② 定位本次生成 `cordis.patch.yml` / `cordis.yml` 是否合法 → ③ 才轮到怀疑插件 `apply()` 抛错。误把正常插件当坏插件误禁是自救的成本,副作用要在插件页明确提示「已自动禁用,可能因插件本身问题或生成配置失败」。

## 40. Tauri 自定义协议窗口内 JS fetch 绝对 scheme URL:Windows WebView2 上全灭(v0.116.6)

**现象**:Obscura 直播查看器窗口(`obscura-live://localhost/ai/index.html`)页面能正常渲染(地址栏/按钮都在),但永远停在「连接 Obscura…」,无帧、输入(地址栏回车/点击/按键)也全部无效;引擎进程与 CDP 会话其实都正常。

## 41. 隐藏回显过滤器常驻扣字:终端行尾 `_` 丢失/成双(v0.116.7)

**现象**:SSH 交互终端里,输入 `_`(或 Tab 补全到以 `_` 结尾的文件名)时下划线不显示,继续敲键后才与后续输出一起「一次蹦出」;看起来像「下划线丢失」或「输入一个显示两个」。

**根因**:OSC 7 注入命令(`__starhub_osc7()…`)的回显由前端 `createHiddenEchoFilter`(`vendor/deepseek-harness/packages/starhub/client-nav/src/client/terminal/terminal-cwd.ts`)整行隐藏。该过滤器是**常驻**流式过滤,对每个 chunk 做三类扣留判定:未完成行含 marker 完整文本、含 marker 的 ≥8 字符前缀、尾部与 marker 前缀重叠——而 marker `__starhub_osc7` 以下划线开头,任何以 `_`、`__`、`__s`…(最长 13 字符前缀)结尾的未完成行都会被扣到下一个 TCP 分片到达才放行。交互式 bash 逐字节回显,行尾 `_` 每次都被扣住,与下个 chunk 的输出粘在一起渲染 → 表现为丢失或成双;Tab 补全重绘行尾恰为 `_` 时同样丢失。

**后续硬约束**:
- 渲染路径上**禁止常驻的流式扣留过滤器**;需要隐藏注入回显时,用「一次性武装 + 回显消费即解除 + 缓冲上限兜底」语义。
- 为回显隐藏挑选 marker 字面量时,避免以行尾常见字符(尤其 `_`、`-`)开头——一旦将来再引入前缀重叠逻辑,这类 marker 会重新扣字。
- 同族镜像实现(`legacy-core/utils/sshPromptCapture.ts`)已无运行时引用,若复用须同步改造。

## 42. disconnect 与代次无关联 + 死会话滞留:关闭后重连连不上(v0.116.8)

**现象**:① 连接 → 关闭 → 再连接,有时报 `Connection aborted by client`,或终端看似连上但键盘输入静默丢弃(ssh_write 找不到写通道返回 Ok);② 网络断开后 AI 命令每条都 `[EXEC_FAILED]`,反复重试永不恢复;③ 停止生成无法中断堡垒机 AI exec,阶段1 等选机器扣住会话锁最长 360s,期间同会话命令全部排队。

**根因**:
- `ssh_disconnect` 的失效/清理逻辑与它要作废的连接代次无关联。它先 `sessions.remove(id)` 再 `session.lock().await.disconnect()`——锁被在途 exec 阻塞数秒;期间用户重开连接(新代次 connect),旧 disconnect 醒来后 `invalidate_attempt` 盲目递增**当前**代次 → 新 connect 终检失败;`remove_channel_for_attempt(新代次-1)` 删掉新 shell 写通道;`pending_kb.remove` 删掉新 MFA 应答。
- 会话条目只在显式 disconnect/detach 时移除:网络断开后(shell 读循环只删写通道 + 发 `ssh:close`)死会话滞留 `SshManager.sessions`;`ensure_ssh_session` / `ssh_attach` 用 `contains_key` 当判活 → 死连接被永久复用,AI exec 会话(无读循环)尤其如此。
- 堡垒机 pty exec 路径不注册 `exec_aborts`,`ssh_exec_abort_core` 返回 `Ok(false)` 实际什么都没中断。

**修复**(v0.116.8):
1. `invalidate_attempt_if_current(id, guard)` 代次守卫:disconnect/detach 在触碰任何可阻塞状态前先记录目标代次,清理时守卫不命中(期间有新 connect 开跑)则跳过全部失效、写通道删除与 pending 清理;
2. SshSession 心跳 task 发送失败(15s 节拍,连接驱动退出)置位 `dead` 标志,`is_alive()` 供 `ensure_ssh_session` / `ssh_attach` 复用前校验,死会话经 `SshManager::drop_session` 丢弃并自动重建;AI 域工具对连接级失败(`[EXEC_FAILED]` / not connected / `[CONN_FAILED]`,命令未开始执行)重建后重试一次;
3. 堡垒机 pty 路径统一注册取消句柄,中止信号贯穿复用 / 选机器(阶段1)/ 命令采集(阶段2)三个 `select!`,立即 `[EXEC_ABORTED]` 返回并释放会话锁;中止后通道状态未知,保守丢弃待重建。

**后续硬约束**:
- 一切「以 id 为键的清理」必须与它要作废的代次绑定:先取目标代次,清理时经守卫校验;禁止在可能长时间阻塞的 await **之后**盲目 invalidate 当前代次或删除当前写通道 / pending 通道。
- 会话复用方(`ensure_ssh_session` / `ssh_attach` / 后续任何复用点)必须经 `is_alive()` 判活,禁止用 `contains_key` 当判活;死会话走 `drop_session` 丢弃,不要原地复用。
- 堡垒机 pty 执行的三个等待点(选机器、采集、复用)必须同时 select 中止接收端;新增等待点同理。

## 43. stripTerminalControl 转义分支顺序错误:OSC 分支成死代码,带颜色/标题 PS1 的 prompt 永远识别不出(v0.116.9)

**现象**:SFTP「跟随终端」默认开启,但 `cd` 后面板不跟随;在终端里手敲一次 `pwd` 面板才跳转。OSC 7 注入链路(注入 → shell 每次 prompt 上报)对多数真实环境从未生效。

**根因**(三处断点叠加,任一都足以让自动跟随失效):
1. `terminal-cwd.ts` 的 `stripTerminalControl` 正则备选顺序错误:`/\x1B(?:[@-Z\\-_]|\[[0-?]*[ -/]*[@-~]|\][^\x07]*(?:\x07|\x1B\\))/g` 中 C0 esc-dispatch 备选 `[@-Z\\-_]` 覆盖 0x40–0x5F,而 `]`(0x5D)落在其中——`\x1B]` 被当作「ESC + 单字符转义」吃掉,第三个备选(OSC 完整序列)是**永远轮不到的死代码**。结果:带 OSC 0 标题 / ANSI 颜色的 PS1(Ubuntu 默认 `\[\e]0;…\a\]\[\e[01;32m\]…`)剥离后 payload 残留(`0;user@host: ~user@host:~$`),`isShellPromptLine` 永远不命中 → `shellPromptSeenRef` 永不置位 → OSC 7 hook 永不注入 → cwd 只剩「用户手敲 pwd 的输出行」兜底。
2. prompt 识别后还要等**下一个 chunk** 才注入:连接后直接操作 SFTP、从不敲终端的用户永远注入不了。
3. fish / csh / tcsh 等 shell 对 bash 方言注入命令(PROMPT_COMMAND 语法)免疫,注入只会打印错误行。

## 44. bump-version.mjs 把含 `$` 的条目写坏 AGENTS.md:replace 替换串的 special patterns(v0.116.9)

**现象**:`node scripts/bump-version.mjs patch` 后 AGENTS.md「当前版本」行损坏——条目里的 `ps -p $$` 变成 `ps -p $`,且 `\w\$`+反引号处把**整个文件头**嵌进了表格行中间,文件结构错乱(README.md 同条目正常)。

**后续硬约束**:
- 凡把**动态文本**(用户内容/CHANGELOG 条目/远端输出)塞进 `String.replace` 的替换串,一律用函数式 `() => str`;字符串形式只允许纯静态常量。
- 升版后必须目检 AGENTS.md 的「当前版本」行与 README 的「当前版本」区(或 diff 中确认无结构错乱);条目文本含 `$`、反引号、`|` 时尤其要查。

## 46. DSH 0.1.6 web app 进程 token 认证:就绪探测 2xx 语义失效 + 裸根路径 401(v0.121.4)

- 就绪探测改「任何 HTTP 响应(含 401/303)即服务已就绪」;子进程提前退出的快失败逻辑保留。

**后续硬约束**:

## 47. 跨站 `location.replace` 拿不到 SameSite=Strict cookie:壳落 401 页(v0.121.5)

**现象**:v0.121.4 的 token 适配(第 46 节)上线后,安装版窗口仍出现 401 文本页「dsh web authentication required; reopen the URL printed by dsh web.」。日志显示 Rust 侧一切正常:`auth_url=http://127.0.0.1:3085/?token=...` 已捕获、`dsh web 可用` 返回的就是 tokenized URL;换回旧版本(无认证)即恢复。

**根因**:DSH 0.1.6 的会话 cookie 是 **HttpOnly + SameSite=Strict**(`browser-auth.ts` 的 `sessionCookie`,Max-Age 30 天)。prod 跳板页(`shell-placeholder/index.html`)由 Tauri 从 **`http://tauri.localhost`** 源提供,它拿到 tokenized URL 后用 `location.replace()` 整窗跳转到 `http://127.0.0.1:3085/?token=...`——**这是跨站发起的导航**:Chromium 对这类导航链**不会在 303 之后的请求上发送 Strict cookie**,于是 cookie 虽已写入 jar,重定向到的 `/` 请求却不带它 → 服务器 401。且跳板页已被 401 文档替换,没有任何重试,只能重开应用。实测三角定位(同一 Tauri WebView2 引擎):
- 从 `tauri.localhost` 页 `location.replace(tokenized)` → **稳定复现 401 页**(与用户所见逐字一致);
- 同一 401 页上 `location.reload()` → 恢复正常(cookie 已在 jar,只是没被发送);
- 从 `127.0.0.1` **同源**页 `location.replace`、**新窗口初始 URL**、**原生 `WebviewWindow::navigate()`**(host 发起,`site_for_cookies` 为空)→ 全部正常。

**为什么第 46 节的「隔离烟测」通过而用户侧失败**:烟测用 curl/fetch 复刻——**curl 不受 SameSite 约束,永远带 cookie**;dev 占位页由 node serve 在 `127.0.0.1:3185`,与真实 web(3186+)同源,恰好也掩盖了问题。只有 prod(tauri.localhost 源)暴露。

**修复**(v0.121.5,仍不动 vendor 内核):
- `dsh_web_url` 命令:`ensure_started` 成功后由 **Rust 用原生导航**把主窗口导到 tokenized URL(`app.get_webview_window("main").navigate(url)`);已在目标源时跳过(避免壳内重入把 GUI 重载一次)。setup 后台任务仍直接调 `ensure_started` 预热(不导航),保证全局只有一次导航。
- 两块跳板页(prod `shell-placeholder/index.html` + dev `scripts/dev-dsh-shell.mjs`)**去掉自导航**,轮询只做状态展示与失败自愈;Rust 导航后文档被替换,轮询自然终止。
- `web.rs` 加固:auth_url 捕获兜底 5s → **30s**(就绪探测「任何响应即就绪」远早于 Loader settle 后的 URL 行打印,冷启动错过就退化裸 URL → 同样 401);捕获逻辑提取为纯函数 `extract_auth_url` 并补 4 个单测(LAN 后缀不抢 loopback、浏览器交接提示行同前缀但非 URL、`\r` 容忍)。

**后续硬约束**:
- 壳内凡是「从 `tauri.localhost` 源跳转到 dsh web origin」的导航,一律走 **Rust 原生 `WebviewWindow::navigate`**(host 发起);页面侧 `location.replace/href` 对 SameSite=Strict cookie 无效。
- 验证 cookie 类链路**不要用 curl**(它绕过 SameSite);必须在真实 WebView 里分「同源 / 跨站 / 新窗口初始 URL / 原生 navigate」四种入口各验一次。
- 第 46 节的「shell 导航 URL 一律取 `dsh_web_url` 返回值」硬约束继续有效,且该 command 现在**自带导航副作用**——新增调用方前先读 `commands/harness.rs` 的文档注释。

## 52. obscura 无头后端中文乱码:fontdb 只吃内置字库,零 CJK 覆盖(v0.123.0)

**现象**:obscura 后端(`browser.engine=obscura`)浏览任何中文页面,直播查看器窗口里文本全是方框/乱码;同一页面 webview 后端正常。日文、韩文同样中招,emoji 正常。

**修复**(submodule 内,三处):
1. `inline.rs` `new_with_web_fonts_and_emoji`:内置字库之后加 `db.load_system_fonts()`,**不**注册进 `loaded_families`(不碰 CSS 族匹配的确定性)。生效链路:cosmic-text 的 `Attrs::matches` 只按 `style`/`stretch` 过滤(不看族名),db 内全部面都进匹配键;Han 字符在默认族( Liberation Sans)缺字时,`FontFallbackIter` 走平台回退表(Windows:`Han → Microsoft YaHei UI`,见 `vendor/cosmic-text/src/font/fallback/windows.rs`)在 db 里命中宿主字库。
2. `paint.rs` `svg_font_database` 同样加载系统字体(usvg 的 CSS 式查询语义,只有显式命名 YaHei 之类才走到,聊胜于无);usvg 的 `load_system_fonts` 在 `system-fonts` feature(fontdb/fs)后面,`obscura-render/Cargo.toml` 给 usvg 开了这个 feature。
3. **配套修的既有缺陷(被回退层暴露)**:默认族解析(`resolve_loaded_font` 的兜底分支)此前返回 `font_id: None`——主字体由 cosmic-text 从匹配键里挑(按 `(weight_diff, weight, id)` 排序)。只有内置字库时,权重 500 落到 diff=100 组的 Liberation Sans(id 最小),碰巧正确;加载系统字体后,**Marlett(Windows UI 符号字体,OS/2 weight class 恰为 500)diff=0 排到第一**,所有 `font-weight:500` 的英文 run 被 Marlett 劫持,拉丁文本按符号度量排版(实测:同一标题从 2 行变 4 行,obscura-render 既有单测 `negative_letter_spacing_changes_intrinsic_line_breaks` 挂掉)。修复:兜底分支改为**钉住内置字体 id**(按 CSS 非对称权重匹配选面),`selected_font` 在 cosmic-text shaping 里有绝对优先权,系统字体退回「只做缺字回退」。emoji 同理会改用宿主 Segoe UI Emoji(与 Chromium 行为一致),相应放宽 `emoji_font_is_loaded_only_for_emoji_documents` 的断言为「emoji 面(内置或宿主)」。

**验证**:`cargo test -p obscura-render --features paint` 470 + 112 例全绿(新增 `han_glyphs_fall_back_to_host_faces`,宿主无 CJK 面时自动跳过强断言);`npm run obscura:build` 重打二进制并装船;本地静态服务 + 中文/日/韩/emoji/权重 500 混合页截图目视确认。**注意 obstacle course(33/33)与 render-repros 基准在 companion repo,本次未跑**——改的是字库回退语义,fixture 像素对比在装了 CJK 字体的开发机上会正常偏移。

**教训(可复用)**:
- vendored 引擎类的「渲染/文本缺失」先查它 fontdb/字库的加载策略,再怀疑自己的调用代码;`include_bytes!` + 「Never load_system_fonts」注释是确定性设计的签名。
- 往「匹配池」里加候选(这里是系统字体)会改变**按权重差排序**的主选择:任何 `(weight_diff, …)` 优先的选择逻辑,加同权重更强的候选都会搬家——先用调试测试打印候选键排序,再决定是排除候选还是改选择逻辑(本次选后者:钉 id)。
- cosmic-text 的缺字回退链(db 内全部 style/stretch 匹配面 × 平台回退家族表)是「加一层候选字体」能生效的真正原因;若引擎自己另建了 family→faces 索引(obscura 的 `loaded_families`)并替 cosmic-text 做族匹配,只往 db 加字体对命名族不生效——两处语义都要读。

## 54. pnpm「假性 up to date」:workspace 状态缓存让 lockfile 漏写 importer,干净环境的 frozen install 才说真话(v0.127.0)

**现象**:DSH 0.2.1-alpha.1 升级(v0.127.0)收敛 lockfile 时,把 `vendor/deepseek-harness/pnpm-lock.yaml` 恢复成上游原版后重跑 `pnpm install --no-frozen-lockfile`,pnpm 一律报 "Already up to date"(762ms),**不写入任何 StarHub workspace importer、不加 `unrun`**,连 `--force`、`--lockfile-only` 也一样。但本机 `pnpm install --frozen-lockfile` 也「通过」——直到把 node_modules 挪走模拟 CI 干净安装,frozen 立即失败:`specifiers in the lockfile don't match specifiers in package.json: 2 dependencies were added(@deepseek-ai/cordis@workspace:^, @deepseek-ai/schemastery@link:…)(packages/client/schema-form)`。

**修复/规避**:
1. 同步 vendor 后若 `pnpm install` 行为异常(不写 importer、不收敛),先 `rm node_modules/.pnpm-workspace-state-v1.json`;

3. StarHub 的 lockfile 必须包含全部 workspace importer(`apps/starhub-window`、`packages/starhub/*` 12 个、三个兼容垫片 `packages/client/{schema-form,web-react,runtime}`),否则 CI/release 的 `pnpm --dir vendor/deepseek-harness install --frozen-lockfile` 直接红。

**教训(可复用)**:pnpm 的「up to date」是**缓存驱动的结论**,不是对 package.json 的实时核对。凡是要以「CI 同款命令」做证据的场景,先在排除本地缓存/node_modules 的条件下复现;缓存能骗过一切「快速通过」的判断。


## 56. paramiko 服务端两个静默失败:`check_channel_*_request` 回 0 = 拒绝、`SFTPServer` 构造后不会自启(v0.128.0)

**现象**:去 Tauri 化 M1 给 sidecar 写端到端验证服务器 `test-sftp/exec_server.py`(password 认证 + exec + SFTP 子系统)。exec 通了之后 `client.open_sftp()` 一律 `SSHException: Channel closed`,服务端日志毫无异常;把 `check_channel_subsystem_request` 的返回值从 `paramiko.OPEN_SUCCEEDED` 改成 `True` 后,SFTP 变成 `EOFError`——又一轮静默失败。

**根因(两个,都在 paramiko 的 API 语义里)**:
1. `check_channel_subsystem_request` / `check_channel_exec_request` 的返回值是**布尔语义**:`paramiko.channel.Channel._handle_request` 直接 `ok = server.check_channel_subsystem_request(...)`,而 `OPEN_SUCCEEDED == 0` 是**假值**——回 0 等于拒绝,服务端发 `CHANNEL_FAILURE`,客户端只见 channel 被关。`OPEN_SUCCEEDED` 只对 `check_channel_request`(kind 级,错误码语义)有效。
2. `SFTPServer` 继承 `SubsystemHandler(threading.Thread)`,`start_subsystem` 才是协议循环入口;只构造不 `start()`,线程永不运行,客户端发完版本号后只等到 EOF。

**修复**:

```python
def check_channel_subsystem_request(self, channel, name):
    if name == "sftp":
        sftp = paramiko.SFTPServer(channel, "sftp", self, sftp_si=StubSFTPInterface)
        sftp.start()          # 不 start() 只有 EOF
        return True           # 回 OPEN_SUCCEEDED(=0)= 拒绝
    return False
```

另两个附带坑:`sftp_si` 必须是 `SFTPServerInterface` **子类**(传字符串路径会被当类调用 → TypeError);服务端宿主机密钥要全程复用一枚(`add_server_key` 放 `handle_client` 里每次连接新生成会让客户端 TOFU known_hosts 永远对不上)。

**教训(可复用)**:paramiko 的 `check_channel_*_request` 家族有**两套返回语义**(kind 级用错误码常量、exec/subsystem 级用布尔),混用不会报错、只会静默拒绝;服务端任何「无异常但客户端被关通道」的现象,先查这两个回调的返回值真值性。

## 57. vitest/jsdom 下 `window === globalThis`:先写后取会把测试替身存成还原值(v0.128.0)

**现象**:去 Tauri 化 M2 把 `client-nav` 的 38 个 spec 从 `__TAURI_INTERNALS__` 存根迁到 fetch/SSE 替身(`tests/host-bridge.ts`)。替身助手第一版写作「先写 `globalThis.fetch = stub`,再把 `window.fetch`(以为还是原值)存进 restore 变量」。结果 `restoreHostBridge()` 之后替身**仍在位**,后续不装替身的用例全部拿到 404——而且失败点离根因很远(某个无关 spec 突然红),极易误判成产品代码问题。

**根因**:jsdom 环境里 `window` 与 `globalThis` 是**同一个对象**(jsdom 把 window 挂成全局)。「先写 globalThis 再从 window 读」读到的就是刚写进去的替身本身,还原值 = 替身,restore 变成把自己再写一遍。Node 原生环境(vitest 的 `environment: 'node'`)没有这个陷阱,所以同一份助手在两种环境下行为不一致。

**修复**:装/拆一对值**先取后写、各取一次**——

```ts
const originalFetch = globalThis.fetch          // 先取原值
const originalWindowFetch = window.fetch        // 同一对象,但也显式取
globalThis.fetch = stub                         // 再写(只写一次)
// restore:两个原值都写回去
```

**教训(可复用)**:凡是「替换全局 + 事后还原」的测试助手,在 jsdom 下必须**先取原值再写入**,并且显式认知 `window === globalThis`;判断某环境的全局是不是同一个对象,一行 `window === globalThis` 就有答案。跨 spec 污染的典型征兆是「单独跑全绿、连着跑才红」或「红在离替换点很远的用例」。

## 58. GitHub Actions 工作流文件非法:一个 job 都不起、秒级 failure,只留一句「workflow file issue」(v0.128.1)

**现象**:去 Tauri 化 M4 第 3 步把 `linux-compat.yml` 换成 `ci.yml`、重写 `release.yml`,推上去之后 Actions 页每条 run 都是 **completed / failure、耗时 0s、`jobs` 为空**,只有一句「This run likely failed because of a workflow file issue」,没有任何步骤日志。`gh run view --log-failed` 回 `log not found`,`/jobs` 回 `{"total_count":0}`,run 还不能 rerun。`v0.128.0` 的 tag 推出去也没产出任何 Release(上一个 Release 还是 v0.126.0)。

**根因**:步骤名写成

```yaml
- name: Smoke: provisioning + host boot
```

值里那个 `: `(冒号加空格)在 YAML 里是**映射条目分隔符**——`name` 的值被解析成 `Smoke`,后面 `provisioning + host boot` 变成它下面的嵌套映射,而 YAML 不允许紧凑映射里再套映射,整份文件非法。`ci.yml` 与 `release.yml` 两份都中招。GitHub 加载不了工作流文件,于是**根本不实例化任何 job**。

**本地为什么发现不了**:本地从不跑 CI——`npm run test:provision` / `test:migrate` / `smoke:dsh-desktop` 都是直接 `node` 跑,不经过 GitHub。那段时间所有「绿」都是本机单测的绿,和 CI 半毛钱关系没有。

**排查顺序(下次照着走)**:

1. `gh run list` 看是不是**所有** run 都 0s failure——是,就别去看 runner / 额度 / 网络;
2. `gh api repos/<r>/actions/runs/<id>/jobs` 回 `total_count: 0` → 工作流文件没加载,不是步骤失败;
3. 拿 YAML 解析器过一遍 `.github/workflows/*.yml`。**js-yaml 的报错信息很差**(只给 `bad indentation of a mapping entry` 加一个指错行的 snippet),换 `yaml@2` 一句「Nested mappings are not allowed in compact mappings at line 107, column 15」直接点中;
4. 定位手法:扫描所有**裸标量**的值里有没有 `: `——这比等解析器报错更早、更具体。

**修复**:步骤名加单引号——`- name: 'Smoke: provisioning + host boot'`。

**护栏**:`tests/workflows-yaml.test.mjs` + `npm run test:workflows`(已作为 `ci.yml` 里最早的一道步骤):

1. 用 vendor 树的 js-yaml 解析每个工作流文件,断言至少声明了一个 job;
2. 扫描所有裸标量的值,含 `: ` 即失败。

反向验证过:把冒号塞回 `ci.yml`,新测试 2 条红;恢复后 3 条全绿。

**教训(可复用)**:① **「工作流文件合法」和「CI 真的在跑」是两件事**,前者只能在 Actions 页上确认,或者像这样加一道最便宜的门;② 任何「值里带冒号」的 YAML 标量都要加引号——GitHub Actions 的 `name:` / `run:` 尤其容易踩,因为步骤名天然爱用「动词: 宾语」;③ 同类症状还有「run 成功但 Release 没正文」:提取 Release 正文的 awk 用整行相等匹配 `## [x.y.z]`,而标题永远带日期(`## [x.y.z] - YYYY-MM-DD`),必须用前缀正则,并且提取为空要 fail loud 而不是 warning。

## 61. Windows PowerShell 下 `npm run <script> -- --flag` 的 flag 被吞:CI 上静默退化成默认分支(v0.129.1)

**现象**:`npm run plugin:bundle -- --pack --dry-run` 在 PowerShell 里跑,脚本**收不到** `--pack`/`--dry-run`(打印的是「只组装不打包」那一支);同一条命令直接写成 `node scripts/build-plugin-bundle.mjs --pack --dry-run` 一切正常。用 `node -e` 显式 `spawn('npm.cmd', ['run','plugin:bundle','--','--pack','--dry-run'])` 也能正常送达——也就是说**问题出在 PowerShell 原生命令的参数传递**,不是 npm。

1. **别依赖 `--` 传参**:脚本需要固定 flag 时,专门开一个 npm script(本仓库新增 `plugin:pack` = `node scripts/build-plugin-bundle.mjs --pack`),CI 与人都只写 `npm run plugin:pack`。

**教训(可复用)**:① 「本地跑过了」要区分**怎么调的**——`npm run x -- --flag` 在 Windows PowerShell 上不等于 `node x --flag`,而 CI 的 windows job 正好是 pwsh;② 给脚本加 flag 的时候,顺手给它配一个 npm script 别名,比依赖 `--` 稳;③ 这类「参数没到」的故障不会报错,只会走默认分支,所以默认分支要做成安全的(本脚本缺 `--pack` 时只组装、不产出半成品 tarball)。

## 64. sidecar stdio 循环串行 + 事件排队:交互式提示永远迟到,首次连接必失败且整个方法面一起卡死(v0.132.2)

**现象**:桌面端「新建连接」点「测试连接」恒停在「测试中…」;同一个对话框点「创建」也毫无反应;进一步实测,只要有一个连接在等,StarHub 工具页的一切命令(资产列表、创建、保存)全部排队卡住,看起来像界面死机。服务器本身完全正常:TCP 130ms 通、banner 立刻返回 `SSH-2.0-OpenSSH_7.4`。

**根因**(两层叠加,都在 Rust sidecar):

1. `main.rs` 的 stdio 循环**逐帧串行**处理,异步域 handler 用 `Runtime::block_on` 在循环线程上跑到完成(`methods/mod.rs` 的 `register_async!`)。一个 SSH 连接最长可等 370s(认证窗口),期间循环线程既不读 stdin 也不处理别的帧。
2. `NotificationSink` 把域事件塞进 mpsc 队列,只有**一条请求跑完**才 `flush_events()` 写 stdout。而「主机密钥确认 / keyboard-interactive MFA / 堡垒机选机器」这三类提示,恰恰是**等待中的那个请求**要求对端回答的东西:提示要等请求结束才发得出去 → 对端根本看不到提示 → 前端为回答它而发的 `ui.ssh_hostkey_response` 又排在同一个管道里读不进来 → 必然 `[HOSTKEY_TIMEOUT]`。

实测(真二进制 + 前端的真实帧序):请求发出后 **60.4 秒**才收到 `ssh:hostkey-confirm` 事件(此时 60s 超时已到),随后补答只得到 `No pending hostkey prompt`;同窗口内 `ui.get_assets` 每 5s 一次全部超时。host key 已在 known_hosts 里时不会触发提示,所以只有**新主机**受害——而 `known_hosts` 一开始就是空的,等于「任何第一次连接都连不上」。

**修复**:每条入站帧各起一个工作线程(`std::thread::spawn`,handler 内部照旧 `block_on`——从非 runtime 线程调用是 tokio 明确支持的),`FrameContext` 改持 `Arc`;事件出口改为**产生即写**(`write_line` 直接锁 stdout 写一行,行结束即刷)。响应按 JSON-RPC `id` 配对,乱序返回对 TS 侧 `JsonRpcLineTransport` 的 `pending` 表无害;同一请求内「事件先于响应」的因果顺序仍成立(事件在 handler 返回前就写了)。

修复后同一帧序:117ms 收到 `ssh:hostkey-confirm`,应答 1ms 内被接收,请求 119ms 内结算;在途期间 `ping` 15ms 返回。回归测试 `a_pending_request_does_not_block_the_next_one`(protocol.rs)用「5 秒本机命令 + 紧随其后的 ping,断言 ping 先回」把这条不变量钉住,不依赖网络。

**教训(可复用)**:① 「串行处理请求」在**有交互式回调**的协议里必然死锁——只要 A 请求的完成依赖 B 帧,而 B 帧只能等 A 结束才被读,就是自锁;设计帧循环时先问「有没有哪类请求要等对端发下一帧」;② 「为了因果顺序而排队」要分清**顺序**与**时机**:事件晚发能让对端先看到因,但也会让提示永远赶不上时限;③ sidecar 这种「宿主替它等」的边界上,任何「请求→提示→应答」链路都要有端到端冒烟,单测里 stub 掉提示就等于没测。

## 65. 工作台 A 组资产 CRUD 参数形状与 sidecar 契约不一致:点「创建」只得到「缺少 id」(v0.132.2)

**现象**:「新建连接」填完点「创建」,对话框不关、列表里也没有新连接;用户视角是「保存不了」。同一对话框的「编辑 → 保存」同样无效。

**根因**:前端按 Tauri command 契约把配置包在 `params` 里下发(`tauriInvoke('create_asset', { params: {...} })`,与 `docker_test` / `db_*_test` 等 113 个调用点同形),而 sidecar 的 `ui.create_asset` 读的是**平铺**字段并要求 `id` 必填(`ui.rs::upsert_asset` 里 `required_str(params, "id")`)。实测同一份负载:`{"cmd":"create_asset","args":{"params":{…}}}` → `{"ok":false,"error":"缺少 id"}`。附带两处漂移:分组键前端发 `group_id`、sidecar 读 `groupId`;sidecar 自己的协议测试用的是平铺形状,前端单测 stub 掉 invoke 只断言了形状,两端从没对上跑过。

**修复**:`ui.upsert_asset` 受理两种形态(`params` 是对象时解包)、`id` 缺省时由 sidecar 生成 uuid(与 Tauri 版 `create_asset(name, type, config) -> Asset` 同一约定)、`groupId`/`group_id` 都认;未下发的字段沿用既有行(改名不再顺手清空 tags/favorite/分组,也不再因缺 `type` 报错)。回归测试:`ui_create_asset_accepts_the_workbench_wrapped_payload`(protocol.rs)直接用工作台的真实负载,并覆盖「update 的 id 在顶层」这一形态。

**教训(可复用)**:① 「调用点零改动」的重写必须为**每一种参数形态**留一条真二进制契约测试——stub 掉的单测只能证明前端发了什么,证明不了后端收得下;② 参数键名的唯一事实来源是 handler 的读取代码(§27 同款),拼写(`groupId` vs `group_id`)要在契约测试里逐个钉;③ 「必填字段」在跨进程契约里要问清楚是**谁**生成:前端对话框压根没有 id 这个概念时,要求它传 id 就是把责任放错了边。

## 66. approval-bridge 抢在 permission-presets 前钉 ask:用户选的「完全权限」被降级成「工作区内修改」(v0.132.2)

**现象**:设置 → 通用 → 权限选「完全权限」,新开会话的文件策略仍是「工作区内修改」;装 StarHub 插件之前一切正常。

**根因**:`starhub-approval-bridge` 在 `session/created` 上执行
`if (ctx.approval.overrideOf(session) !== undefined) return; setApprovalPolicy(session, 'ask')`,
而它的监听器先于 dsh `permission-presets` 的同名监听器触发,于是新会话在 dsh 落 preset 之前就被写入了 `approval/policy=ask`。`permission-presets` 的 `pinInitialPermission` 用「preset/sandbox/approval 三者全空」判定**全新会话**,被写脏后走了「半初始化」分支——缺的 sandbox 用**进程默认值**补,而不是用 `defaultPreset`:用户选的 danger-full-access 被替换成 workspace-write。

会话日志是铁证(同一个 profile):装插件前的会话 `seq0 permission/preset=danger-full-access → sandbox/mode=danger-full-access → approval/policy=never`;装插件后的新会话 `seq0 approval/policy=ask → permission/preset=workspace-write → sandbox/mode=workspace-write`。

**附带的危险方向**:这个分支用「进程默认」补空缺,所以把默认预设设成「只读」时,新会话拿到的同样是 workspace-write——**权限被放大**而不只是被缩小。

**修复**(按用户决定「完全尊重 dsh 预设」):组合里有 `permission-presets` 时本桥不写任何权限事实(只有没有它的内嵌组合才保留钉 ask);风险门改为读**会话生效策略**,策略为 `never` 时直接放行——`dsh-user-approval` 的 `decide()` 在 never 下先于所有 answerer 直接拒,制造注定被驳回的 ask 等于 StarHub 私自推翻用户选的预设。原「hard 死规定(删除/高危档任何预设都必须确认)」与 never 语义不可兼得,随之下线,`classifyStarHubCall` 只保留 ask 分级。回归测试:`permission-policy.spec.ts`(真 `Context` + 真 `ApprovalService` + 真 `SessionStore`)钉住「有 preset 服务时不写权限事实」「无 preset 服务时钉 ask」「never 下风险门放行」。

**教训(可复用)**:① 多个插件监听同一个生命周期事件时,**谁先写**决定语义:消费别人的「初始状态判定」之前必须确认自己没把那个判定打脏,`session/created` 上「只填空缺」的写法在监听器顺序不确定时是不安全的;② 「填空缺」的兜底值必须与被填空的东西同源(preset 的 sandbox 该来自 preset,不是来自进程默认),否则缺得越多错得越远;③ 权限类改动要拿**会话日志**当证据,别只看界面——`seq0` 是谁写的、写了什么,一读便知。

## 67. `ui.get_assets` 不带密钥:SSH 终端与所有数据库面板恒以空密码认证(v0.132.3)

**现象**:主机密钥确认点「信任并保存」后,SSH 终端立刻报 `[AUTH_FAILED] Authentication rejected and no further methods available`。服务器侧一切正常:`ssh -o PreferredAuthentications=none` 明确回 `Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password)`——password 方法是**开着**的;资产也确实建好了(`authMode: "password"` 且 `key_id` 非空,说明密钥落了库)。

**根因**:M2 把资产清单搬进 sidecar 时定义了「`ui.get_assets` 不含密钥」(`to_ui_json` 只回 `record.config`,敏感字段早被 `split_config` 拆进 `SecretStore`),协议测试还专门断言了这一点;而**工作台的连接面全部从 `asset.config` 取密码**——SSH 终端 `buildSshAuth(config)`(`config.password` 取不到就回退 `{ Password: '' }`)、`DbWorkbench`(注释写着「config 由 get_assets 经 keyring hydrate 含密码」)、Redis/ES/Docker/broker 面板同理。两端语义相反:前端以为拿到的是**合并密钥后**的配置,后端给的是拆过密钥的配置。于是每次建连都在用空密码认证。

**为什么前端敢这么写**:Tauri 版的 `get_assets` 经 keyring hydrate 返回明文密码,这套前端(从 Vue 版逐行移植)就是照那个契约写的。M2 单方面改了返回语义却没改调用方,而双方的单测都绿:前端 stub 掉 invoke 只断言「我发了什么」,sidecar 的协议测试只断言「我回了什么」。

**修复**:`ui.get_assets` 恢复 Tauri 语义——UI 面清单返回**合并密钥后**的配置(`load_asset_config(record.id)`),密钥缺失/存储损坏时退回未合并的配置(清单照常打得开,认证失败在执行点报);模型面 `starhub_list_assets` 的文本摘要仍只取非敏感字段(模型永远看不到密钥)。协议测试的断言随之翻转为「清单必须带密钥」,`ui.rs` 单测补同口径断言。

**教训(可复用)**:① 跨进程契约里「返回值的语义」也是契约——**去掉一个字段和改一个字段名一样危险**,尤其当字段是被有意「拆走」的敏感数据;② 移植前端时,凡是「前端从 asset/entity 上直接读某个字段去建连」的地方,都要问一句这个字段在**新后端**里还在不在;③ 双侧单测都绿不等于契约一致:stub 只能证明一侧的行为,跨进程边界必须有一条**真二进制**的端到端断言(本案是「`ui.get_assets` 的响应里必须有 `config.password`」)。

## 68. 用 dsh 内置浏览器打开 StarHub 页面必然白页:guest 会话禁止请求宿主源(v0.133.0)

**现象**:把 StarHub 独立工作台页(`http://127.0.0.1:19387/starhub-react/index.html?asset=…`)粘进 dsh 的**内置浏览器**(侧栏浏览器 / webview guest)打开,得到一片白页;同一个 URL 用系统浏览器(Chrome/Edge)打开完全正常。

**根因**:这是上游 Electron 壳的**安全策略,不是页面 bug**。[browser-guests.ts](../../vendor/deepseek-harness/apps/desktop/src/browser-guests.ts) 给每个 guest 会话装了请求拦截与导航白名单:

- `configureSession().webRequest.onBeforeRequest`:`isApplicationHost(url)` 命中即 `cancel`;
- `allowedNavigation(url)`:命中即返回 false(阻止导航);
- `isApplicationHost(url)`:端口等于 DSH 宿主端口,且 hostname 是宿主 hostname 或 `localhost`/`127.0.0.1`/`[::1]`。

注释写得很直白:「current authenticated DSH Host, **which guests cannot request**」——guest 用的是独立 partition(没有宿主 cookie),但宿主 API 在回环上并不校验 cookie(我们实测 PowerShell 裸调 `/starhub/api/invoke` 也是 200),所以壳必须自己把整个宿主源挡在 guest 之外。StarHub 的所有页面(壳内面板 + 独立工作台页)都在这个源上,于是内置浏览器里一律白页。

**结论/规避**:想看独立窗口就用**系统浏览器**;内置浏览器只适合访问外部站点。真要让内置浏览器能开,只能改上游壳的策略(把宿主源从 deny 列表里放出去),那等于让任意 guest 页面都能打宿主 API——不做。

**后续(v0.133.1)**:「在浏览器中打开」一开始走前端 `window.open`(指望壳把它转 `shell.openExternal`),实测点了没反应——这一环依赖壳的实现细节,且前端异常会被静默吞掉。改为 **sidecar 直接唤起系统浏览器**(`ui.open_external_url`:Windows `rundll32 url.dll,FileProtocolHandler` / macOS `open` / Linux `xdg-open`,参数向量直达进程、不经 shell,URL 里的 `&` 不会被解析),`window.open` 只作回落。教训:跨进程/跨进程边界的「打开外部程序」不要建立在别的进程的策略细节上,自己这一层能做的就自己做完。

**教训(可复用)**:① 「白页」先分三类:页面自身 boot 失败、跨源被拦、资源 404——内置浏览器属于第二类,证据在壳的 webPreferences/webRequest 策略里,不在前端;② 壳为 guest 设的隔离策略会**顺带**挡住自家页面,规划「面板页 / 独立窗口」时先查 `allowedNavigation` 与 `onBeforeRequest`;③ 需要独立窗口的功能,出口是系统浏览器或壳新增 IPC,别指望内置浏览器;④ 「唤不起外部程序」这类静默失败要在**自己可控的一层**兜底(sidecar 直接 spawn),别把行为寄托在宿主策略上。

## 70. 桌面壳里 `location.origin` 是 `dsh-app://app`:拿它拼的绝对 URL 全是废的(v0.133.3)

**现象**:「在浏览器中打开」点了之后提示「未能唤起系统浏览器,链接已复制到剪贴板」,而剪贴板里是 **`dsh-app://app/starhub-react/index.html?asset=…&workbench=ssh`**——既打不开,也不像宿主地址。同一台机器上,我直接用 `POST /starhub/api/invoke {cmd:'open_external_url', url:'http://127.0.0.1:19387/…'}` 却能正常唤起 Chrome(Chrome 历史记录有对应访问时间戳),说明 sidecar 那半边是好的。

**根因**:桌面壳把主窗口导航到 **`dsh-app://app/`**([main.ts:399](../../vendor/deepseek-harness/apps/desktop/src/main.ts#L399) `applicationUrl = '${SCHEME}://app/'`),再用 `protocol.handle(SCHEME, …)` 把该源下的请求 `forwardWebRequest(request, hostUrl, hostCookie)` 反代到真正的宿主。所以:

- 壳内页面的 `window.location.origin` = **`dsh-app://app`**(不是 `http://127.0.0.1:19387`);
- 相对路径的 fetch / iframe src 都能正常走(被壳反代),**但前端自己拼不出宿主的绝对 URL**;
- 前端拿 `location.origin` 拼出的 `dsh-app://app/…` 会连撞两道门:sidecar 的 `ui.open_external_url` 只收 http/https(直接 -32602),壳的 `setWindowOpenHandler` 也只把 http/https 交 `shell.openExternal`(`window.open` 返回 null)。于是两条路都失败,只剩剪贴板兜底——而兜底的也是废链接。

**修复**:新增**桥内命令** `host_origin`(不下发 sidecar):`starhub-bridge` 在 Node 侧用请求的 `Host` 头还原宿主源(`http://127.0.0.1:19387`,支持 `x-forwarded-proto`),前端据此拼绝对 URL 再交给 `ui.open_external_url`;取不到(浏览器预览 / 旧宿主)时退回页面自身 origin。规则:Host 必须是 `host[:port]` 形态(挡掉空白与斜杠),避免拼出奇怪的 URL。

**教训(可复用)**:① **壳内页面的 origin ≠ 宿主 origin**——桌面壳用自定义协议 + 反代是常见做法,「相对路径能通」不代表「能拼绝对 URL」;凡是需要把地址交给**外部程序**(系统浏览器、外部编辑器)的地方,绝对 URL 必须由**见过真实请求的宿主侧**给出;② 「点了没反应」的排查顺序:先让失败**可见**(本次的剪贴板 + 面板提示就是为此),再把可见证据(这里是一条 `dsh-app://` 链接)当线索,一步就能定位到 origin 假设;③ 用户会把你复制的链接原样粘回来——兜底内容本身也要是**可用**的,不能只求不静默。

```
[386ms] "Last login: … \r\n\r\nWelcome to Alibaba Cloud Elastic Compute Service !\r\n\r\n"
[470ms] "\u001b]0;work@zhht-dev:~\u0007\u001b[?1034h[work@zhht-dev ~]$ "        ← 提示符 1(只有一次,服务端没问题)
[499ms] "__starhub_osc7() { … } \r; then … fi\r\n\u001b]0;…\u0007\u001b]7;/home/work\u0007[work@zhht-dev ~]$ "  ← 注入回显行 + 提示符 2
```

**根因**:打开终端时 client-nav 会静默注入 OSC 7 钩子(SFTP「跟随终端」要实时 cwd),而 `createHiddenEchoFilter` 命中 marker 后把**整行连同行尾 `\n` 一起**丢掉。于是:提示符 1 已渲染(光标停在它末尾)→ 回显行被整行吞掉(连回车换行也没了)→ shell 执行完命令重印提示符 2,只能接在光标处 = 并排两个提示符。**服务端只印了一次提示符,重复完全是客户端渲染造成的。**

**修复**:丢弃回显行的位置**代入行复位** `HIDDEN_ECHO_LINE_RESET = '\r\x1b[2K'`(CR 回列首 + 擦除整行),提示符 2 落在同一行,屏幕上只剩一个提示符;回归用例直接按上面抓到的真机分片写(旧实现下必然产出并排的两个提示符)。

**教训(可复用)**:① 「删一段自己刚刚渲染过的输出」要**连光标状态一起还原**——文本删了、光标没回列首,后一段输出就会贴在残留内容后面;凡自己做行级过滤,必须显式回答「删完之后光标在哪一行哪一列」;② 这类「界面看着是重复/错位」的问题,先抓**原始字节流**(分片 + 时间戳)再读渲染代码:本次一眼能看出「服务端印了两次」和「服务端印了一次、客户端印了两次」的区别,直接省掉对 Rust 侧的怀疑;③ 同一个过滤逻辑在 `legacy-core/utils/sshPromptCapture.ts`(已无运行时引用的旧镜像)里有同形实现,要复用必须先同步改造。

**顺带**:同一次排查里,「区域截图」入口被移除而不是继续挂着报错——能力在去 Tauri 化 M2 已判给 Electron 壳,没有实现面的入口就是**摆设 + 误报来源**(点一次弹一次「暂不可用」)。

## 72. 会话 id 既是 map 键又是事件名:同一资产开两个窗口会串台(v0.133.6)

**现象**:同一个 SSH 资产开第二个窗口,第一个窗口的输入行里凭空出现 `__starhub_osc7() { printf '\033]7;%s\007' "$PWD"; }; if [ -n "${ZSH_VERSION:-}" ]; then …`(第二个窗口打开时注入的 OSC 7 钩子);之后在任一个窗口敲字,**两个窗口都有反应**。用户判断「要相互独立才对」。

**根因**:`SshTerminalOverlay` 的会话 id 直接取 `asset.id`。这个 id 在协议里有两个身份——sidecar 会话表 `SshManager.sessions` 的**键**,以及 `ssh:data:<id>` / `ssh:close:<id>` / `ssh:kb-interactive:<id>` 等事件的**事件名**。于是第二个窗口的 `ssh_connect` 用同一个键 `sessions.insert(id, …)` **覆盖**了第一个窗口的会话(map 里只剩一条),两个窗口:① 订阅的是同一个事件名 → 双方的输出都渲染到两个窗口;② `ssh_write` 也路由到同一条 shell → 输入串台;③ 关掉任一个窗口的 `ssh_disconnect` 把唯一的会话删掉 → 另一个窗口跟着断。第二个窗口注入 OSC 7 时的回显只被**自己**的隐藏回显过滤器吃掉,第一个窗口没武装过滤器 → 那行命令就「出现在第一个窗口里」。

**修复**:每个终端实例生成独立会话 id —— `terminalSessionId(assetId)` = `<assetId>__<6 位 base36 随机>`(36⁶ ≈ 2.2e9),`useState(() => …)` 只在挂载时取一次,同一实例「重新连接」沿用同一个 id(只换连接代次)。真机验证(两条会话前缀同为资产 id、后缀不同):在 A 里 `echo STARHUB-A-ONLY` 只有 A 的流出;给 B 注入 OSC 7 时 **A 的流新增 0 字节**;B 的命令也只在 B 的流出。AI 域工具走的是另一套 id(`dsh:{assetId}:ssh`,见 `starhub-domain-ssh/tools.rs` 的 `ai_conn_id`),不受影响。顺带把「命令广播」列表标题从会话 id 改成「本窗口显示资产名 / 其它窗口显示主机」,不再暴露带随机后缀的 id。

**教训(可复用)**:① **一个标识符同时充当「存储键」和「事件名」时,它就成了全局唯一性的契约**——凡是「同一个东西可能被打开多次」的界面(窗口/标签页/面板),实例 id 必须由实例自己生成,不能复用实体 id;② 复用实体 id 的代价不是「两条连接浪费」而是**静默串台**(覆盖式 `insert` 让两个消费者共享一条链路),排查时先确认「两个窗口的 id 是不是同一个字符串」,再谈前端渲染;③ 顺手核了同类路径:数据库/Docker 的 connId 由 Go sidecar 用 `time.Now().UnixNano()` 生成(每次连接唯一),所以只有 SSH 终端这一处踩了坑——**同类风险要沿着「id 从哪来」逐个确认,不能只修报告的那一处**。

## 73. `ctx.agents.create()` 不打 `meta.cwd`:会话拼不出 `{{cwd}}` 段,回合静默死在第 1 步(v0.134.2)

**现象**:SSH AI 助手面板上发消息**完全没反应**(「看一下 SSH 的 AI 助手,没有反应」);dsh 会话列表里出现「未分组 / 未命名」的 `ssh-assistant-*` 会话;从列表点开历史报 `session "…" not found`。三个症状同一次出现,看着像三个 bug。

**根因**:`starhub-ssh-assistant` 插件以 `ctx.agents.create({ sessionId, … })` 建根 Agent 时**没传 `meta.cwd`**。dsh 会话模型里,无 cwd 的会话(`SessionHeader.cwd === undefined`)有两重后果:

1. **回合必败**:基础包的系统提示模板里有引用 `{{cwd}}` 的段落,提示装配在回合第 1 步对无 cwd 会话抛 `prompt variable "{{cwd}}" has no value for this assembly`——回合以 `turn/end reason.kind=error` 收场,一条消息/工具事件都没产出过;
2. **列表/历史双拒绝**:无 cwd 会话的日志落进 `~/.dsh/sessions/_no-cwd/` 桶,`session.list` 照列(未分组、未命名),但历史加载/agent/技能目录这几条路径一律按 not-found 拒绝。

「没反应」之所以毫无线索,是叠加了第三层:**插件把每条会话事件都经 SSE 原样转发给面板,但客户端 fold 函数 default 分支把 `turn/end` 忽略了**——回合失败事件到了面板门口被丢掉。三层各贡献一个症状:装配抛错(没反应)、`_no-cwd` 桶(未分组/未命名)、历史路径拒绝(session/not-found)。

**修复**:① `open()` 恒打 `meta.cwd`(指向插件专属目录 `~/.starhub/ssh-assistant`,插件 Config 字段 `sessionCwd` 可覆盖,apply 时 mkdir、失败 fail loud)——cwd 有**绝对路径**校验,别传相对路径;② 会话建好后调 `sessionTitle` 服务把显示名钉成**纯服务器名**(user 来源,顺带压住自动标题;服务缺席降级告警不阻塞)——用户明确要「未分组 + 服务器名」而不是隐藏幽灵会话;③ 客户端 fold 补 `turn/end` 错误分支(`reason.kind === 'error'` 渲染为错误项,按 `turn-<n>` 去重,重放不叠加)。排障手法:会话日志是多帧拼接的 zstd,Node 的 `zstdDecompressSync` 只解第一个帧,**必须按帧魔数 `28 B5 2F FD` 切片逐帧解码**才能看到全部回合事件。

**教训(可复用)**:① **凡在插件里 `agents.create()` 建根会话,`meta.cwd` 是事实上的必填**——缺了不会在建会话时报错,而是把失败推迟到回合装配期,且以「什么都不发生」的形式呈现;给这类会话选目录时记住:**cwd 同时决定会话列表的归组**(不匹配任何工作区 → 未分组)。v0.140.2 之前选插件自有目录是为了「未分组」(当时用户诉求);**v0.140.2 起用户改要「归到默认工作区」,同一结论反向适用:cwd 取默认工作区规范路径 + `attachSession` 记入账户才会归组**(双条件与全局注入观感见 §76);② 「AI 完全没反应」的第一怀疑对象不是模型,而是**回合有没有开始**——先解码会话日志看有没有 `turn/start` 与 `turn/end` 的 reason,再看面板丢了哪类事件;③ 转发型 UI 的 fold/渲染层对「未识别事件静默忽略」要留例外清单:`turn/end` 错误、approval 请求这类**不产生其它事件的失败**必须渲染,否则失败不可见;④ 组合测试里提示模板的 `personaPrefix:''` 不带 `{{cwd}}` 段,所以测试环境无 cwd 也能跑通回合——**测试组合与真实部署的提示模板差异会掩盖这类错误**,涉及系统提示变量的改动要对着真实 bundle 验一次。




## 74. SSE 路由 `writeHead` 排在 `attach` 之后:第一帧就冲刷隐式响应头,面板永远「连接中断」(v0.134.3)

**现象**:SSH AI 助手面板显示「连接中断,重新打开本页签可恢复」且**永远空白**;但在 dsh 主界面会话列表里能看到同一个会话(未分组、服务器名),消息发得出、回复也正常(「输入你好,没有在 ssh 端 AI 展示,在第一张图片展示了」)。POST 路由全部正常,只有 SSE 流是死的。

**根因**:`streamHandler` 把 `res.writeHead(200, { 'content-type': 'text/event-stream; … })` 写在了 `registry.attach()` **之后**。而 `attach` 为了给晚到客户端补历史,在注册 write 回调后**同步**重放事件窗口——第一帧就走到 `res.write(...)`。Node 的规则:**第一次 `write/end` 会立即冲刷隐式响应头**(`Date` / `Connection` / `Transfer-Encoding: chunked`,**没有 content-type**),此后的 `writeHead` 抛 `ERR_HTTP_HEADERS_SENT` 且头已追不回来。浏览器 `EventSource` 收到 200 但 MIME 不是 `text/event-stream`,按规范判**致命错误、绝不重试** → `onDrop` → 面板空白。裸 TCP 探针一眼看穿:线上响应头只有 Date/Connection/Keep-Alive/Transfer-Encoding 四项,而同一宿主上 bridge 的 `/starhub/api/events`(先 writeHead 再 write)头俱全。定位手法:① 对比同宿主另一条 SSE 路由排除「宿主剥头」;② Node 最小复现(`write` 先于 `writeHead`)复现线格式与抛错;③ PowerShell 的 `HttpWebRequest` 读 SSE 会假报 14MB 洪水( chunked 读取的假象),**探 SSE 一律用 Node `http.get` 或裸 TCP**。

**修复**:响应头先于任何一帧写出(writeHead → 连接注释 → attach);attach 失败(助手已关闭)时头已发出、状态码改不了,改用 SSE `error` 帧告知面板(折叠成错误项),不再回 200 JSON。测试侧的假 `res` 升级为 **Node 忠实头语义**:首次 `write/end` 冲刷隐式头、其后 `writeHead` 抛 `ERR_HTTP_HEADERS_SENT`——原来的宽容桩「只记录不抛」,正是这个 bug 从 28 个测试眼皮下溜过的原因。顺带修掉面板 boot 竞态:卸载时 `openAssistant` 还在飞,resolve 后竟 `closeAssistant` 把正要被复用的助手会话销毁(逼下次挂载重建、对话丢失),改为直接返回。

**教训(可复用)**:① **流式响应的 writeHead 必须排在第一次 write 之前,没有例外**——「先挂数据源再写头」的直觉顺序在 Node 里正好相反;任何 SSE/流式 handler  review 时先看这两行谁先谁;② 假响应对象的语义要**复刻真实失败模式**:宽容桩让「头丢失」类 bug 永久隐形,该抛的错就要抛;③ 面板「连接中断 + 空白」先裸 TCP 看响应头,再看 EventSource 的 MIME 判定——浏览器不告诉你「content-type 不对」,只给你一个 CLOSED;④ POST 通、SSE 死的故障形态基本可以锁定在响应头/MIME/代理层,不要再去查业务逻辑。

## 75. 去 Tauri 化后的纯转发层丢掉了参数改名:单元格保存/Redis 搜索在真实 sidecar 上静默失败(v0.136.6)

**现象**:数据库表数据网格里双击改单元格、点「保存」看起来走完了流程,但数据没有落库;Redis 左侧每个 db 的 key 搜索框输入后,列表仍返回整库 key(搜索词像没生效)。两者的单测全绿。

**根因**:旧 Tauri command 不是纯转发,而是**逐参数改名**后再 `sidecar.call`:
- `db_mysql_update_rows(where_clause)` → Go `db.mysql.updateRows` 的 `where`;
- `db_redis_scan(match_pattern)` → Go `db.redis.scan` 的 `match`。

去 Tauri 化 M2 把这层薄封装搬进 Rust sidecar 时改成了 `Shape::Flat` 纯平铺转发(参数原样下发),但前端调用仍沿用旧 Tauri 的 camelCase 参数名 `whereClause` / `matchPattern`。于是:
- `update_rows` 被 Rust 的 required 白名单判成缺参(「缺少 where」),每次保存必失败;
- `redis.scan` 不校验可选参数,`matchPattern` 被 Go handler 忽略(它只解 `match`),搜索退化为全量 SCAN——**静默**失效,连报错都没有。

单测用同一个错误参数名打桩(`expect({ whereClause })` / `expect({ matchPattern })`),把 bug 完全掩盖;只有真 sidecar + 真 Rust 转发层才会暴露。

**修复**:前端改为 sidecar 契约参数名(`where` / `match`),并在测试里断言新名字。顺手复核了同期迁移的其余 C 组命令:旧 Tauri 层做过改名的只有这两处(其余参数名两端一致)。

**教训(可复用)**:① **「薄封装」也是契约的一部分**——迁移掉一层时,先把它做过的所有参数改名/默认值列出来,再决定是保留映射还是改调用方;纯转发层不会替你兜底。② 参数校验分两种:required 缺参**会报错**(update_rows),可选参数写错名**完全静默**(scan),后者更危险——新增/迁移可选参数时优先按 handler struct 的 json tag 逐字核对。③ 单测里把宿主桥接成 mock 时,**期望值本身也可能错**;涉及跨进程契约的参数名,至少要有一处对着 Rust `Spec.required` 或 Go handler tag 的断言/评审,不能只靠「两边用同一个字符串」。④ 与 §27「Rust ↔ sidecar 参数键名漂移」是同一类坑的第二次出现:这次漂移发生在**前端 ↔ Rust 转发层**,排查时要把调用链上每一跳都当作独立契约看。

## 76. 「SSH AI 有我未分组会话的上下文」是同一个会话的两个视图,外加一处命令级的跨会话注入(v0.140.2)

**现象**:用户发现 SSH 终端页的 AI 助手「有我未分组 session 的对话的上下文」,怀疑上下文串话。排查结论:**对话原文一个字节都没有跨会话**,是两件事叠在一起造成的观感。

**根因**(两层,各自独立):

1. **未分组里的那些会话就是助手自己的会话(主因)**。v0.140.2 之前每个助手会话的 cwd 是 `~/.starhub/ssh-assistant`,不匹配任何工作区 → 全部落「未分组」,标题被 `sessionTitle` 钉成服务器名——列表里看上去就是一条条名为「web01」的普通对话。面板与主壳列表操作的是**同一个 agent 会话的同一条 durable log**:在面板里聊 = 写进那条未分组会话;在列表里点开它 = 看到面板里的全部对话(SSE `session/event` 转发 + `attach` 重放);在主壳里接着输入 = 面板(若开着)实时同步。终端窗口重开会换新 `sshSessionId`(`terminalSessionId` 每次挂载随机),旧会话留在列表里变成历史。所以「助手有我未分组会话的上下文」= 那个会话本来就在助手自己身上。
2. **`starhub-live-context` 的 pre-step 注入是全局的(真实存在,但只到命令级)**。它每个 agent 每一步注入:`[Session registry]`(sidecar 活跃会话)、`[Recent events]`(领域事件,含 AI 起源)、`[Recent AI execs]`(**每资产最近一次 AI 工具执行 + ≤2KB 输出尾部**)、`[Task trails]`,整段 ≤4000 字符。recentExecs 是 sidecar 级全局缓存(`after_tool_success` 写入,**不区分是哪个 agent 会话**):主壳 AI——包括未分组会话里的对话——通过 starhub 工具跑过的域命令同样进缓存,SSH 助手因此能在上下文里看见「你刚让别的会话跑了什么命令、输出尾部是什么」。这是有意设计的活性上下文,不含对话原文。对照:`starhub-tool-context` 的注入是**会话级**的(只对触发绑定的会话注入),两个插件的作用域不对称,排查时容易忽略后者。

**修复/处置**:v0.140.2 把助手会话归到默认工作区(cwd = 工作区规范路径 + `attachSession`),未分组不再堆助手会话,混淆源消除;live-context 的全局注入保持原样(产品设计),如某部署要求更严隔离可 `enabled: false` 或把 recentExecs 按会话收敛——那是产品决策,不在本条目动。

**教训(可复用)**:① **「会话归属」观感问题的第一嫌疑是 cwd**:dsh 会话列表按「账户 + 会话头 cwd 等于工作区路径」归组,插件自建会话不给工作区 cwd 就一定进未分组——先确认那个「未分组会话」是不是插件自己的会话,再怀疑串话;② 排查「AI 怎么知道这事」要沿 **pre-step 注入链**逐个插件看(本仓库只有 live-context / tool-context 两个注入点),并分清**会话级**与**全局级**作用域;③ 同一会话的多视图(面板 SSE + 主壳列表)不是泄漏:任一端输入,另一端实时同步,是同一 durable log 的两个渲染出口。
