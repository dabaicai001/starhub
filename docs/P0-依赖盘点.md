# P0 依赖盘点 —— 独立插件与宿主工作区改造

- 日期：2026-11-16
- 上游方案：`docs/StarHub-独立插件与宿主工作区改造方案.md`（下称「总方案」）
- 目标宿主：官方 DeepSeek Harness `0.2.2-rc.3`
- 状态：**P0 完成**（本文件即 P0 交付物，未改动任何运行时代码）

## 1. 结论摘要

1. **P1 可行且成本可控**。用官方 npm 包（`0.2.2-rc.3`）替换 vendored 源码后，StarHub 自有源码的编译面只剩 **2 类共 6 个错误**：
   - Host 面 4 个：`@deepseek-ai/dsh-sdk-jsonrpc-server/src/notifications.ts`（StarHub 私有补丁文件，上游无此文件）被 2 个插件导入，连带 2 处 `implicit any`。
   - Client 面 2 个：`@deepseek-ai/dsh-client-runtime/client`（该包已被上游删除，靠 StarHub 垫片顶上）+ 1 处 `Menu` 属性在 `exactOptionalPropertyTypes` 下的漂移。
2. **只有 1 处上游补丁是 StarHub 独有的**（`packages/sdk/server` 的 `sdk-transport` / `sdk-notifications` 服务补丁）。它只服务已退役的 Tauri/SDK 组合；bundle 形态下同名服务由 `packages/starhub/bridge/src/compat.ts` 自己提供。**因此该补丁可以随 vendor 一起删除**，代价是把 `SdkNotificationHub` 类型（10 行）搬到 StarHub 自己的包里。
3. **vendor 里 99% 的源码 StarHub 不引用**。`git grep -l -i starhub` 在 vendor 的 `packages/ apps/ examples/ scripts/ *tsconfig* pnpm-workspace.yaml` 范围内只命中 **14 个文件**，逐个归类后没有一个是「必须保留的上游改动」：StarHub 垫片 3 个（`packages/client/runtime`）、上游补丁 3 个（`packages/sdk/server`）、把 StarHub 登记进上游 workspace 的配置 5 个、StarHub 自己的构建脚本 3 个。
4. **npm 侧缺口只有 3 个包**，都有明确替代方案（见 §3）。

### 4.2 `sdk-notifications` 补丁的处置

现状：`packages/sdk/server/src/index.ts` 在 patch 里 `ctx.provide('sdk-transport' | 'sdk-notifications')`，供 9 个插件消费。上游 `0.2.2-rc.3` 没有这两个服务（已核实 installed tarball 无 `src/notifications.ts`）。

但 **bundle 形态本来就不用它**：`packages/starhub/bridge/src/compat.ts` 已经自己 `provide` 同名服务（`BRIDGE_TRANSPORT_SERVICE` / `BRIDGE_NOTIFICATIONS_SERVICE`），并且 README 明确写「两者只能有一个在场，否则 duplicate service 硬失败」。`examples/starhub-desktop/cordis.patch.yml` 的注释也写明 desktop 组合用 bridge 取代 `sdk-jsonrpc-server`。

因此：

1. **删除** vendor 里的 SDK server 补丁（P3 随 vendor 一起消失，P1 前先把我们自己的类型落地）。
2. 把 `SdkNotificationHub`（`subscribe(method, handler: (params: unknown) => void) => () => void`，10 行）搬到 `packages/starhub/bridge` 的公开子路径（`./compat`），`domain-events` 与 `session-registry` 改为 `import type { NotificationHub as SdkNotificationHub } from '@deepseek-ai/dsh-starhub-bridge/compat'`。
3. 不新增运行时耦合：该导入是 `import type`，编译期擦除。

> 备选（未采用）：在每个消费包内联一份 interface。否决理由：`bridge/compat.ts` 已经是这套宿主私有协议的唯一定义地（方法名常量、peer 接口都在那里），再复制一份就是第二个家。

### 4.3 其它移植注意

- `client-nav` 的 `tsdown.config.ts` 依赖上游预设 `packages/client/tsdown.client.ts`（693 行，含 client bundle 的 externals/CSS/`__ModuleLoader__.load({id})` 包装）。**必须自建等价预设**，不能 import vendor 文件。
- `apps/starhub-window/vite.config.ts` 把上游包 alias 到 vendor 源码（为了 CSS 走 Vite 管线）。迁出后只能 alias 到 **StarHub 自己的** `client-nav` 源码；DSH 侧改由 npm 包解析。**样式完整性需目视验收**（P5）。
- `packages/starhub/*/tsconfig.json` 的 `references` 全部指向 `../../client/*` 等 vendor 路径，需改成「无引用 + 从 node_modules 解析」或只引用 StarHub 自己的包。

## 7. 阻塞项与风险

| 风险 | 影响 | 处置 |
|---|---|---|
| `client-nav` 的 tsdown 预设要自建 | client 半边打包不出来 | P1 内自建最小预设（externals 基线 + `__ModuleLoader__.load` 包装）；用冒烟五条断言兜底 |
| `ClientRemote.settings` 在 0.2.2-rc.3 不存在 | client 面 1 个编译错误 | P1 内按新版 API 改写（读 `ctx.settings` 或等价） |
| `Menu` 属性 `exactOptionalPropertyTypes` 漂移 | client 面 1 个编译错误 | P1 内改调用点（不传显式 `undefined`） |
| 工作台样式依赖 vendor 源码的 CSS 管线 | 迁移后工作台可能掉样式 | P1 只要求构建通过；样式完整性放 P5 目视验收（总方案 P1 门槛未含视觉） |
| 官方预发布 semver 兼容门 | `engines.dsh` 写错会装不进 | 保持现有 `engines.dsh` 不动，P2 用真实安装验证后再定 |
| release workflow 仍构建上游 Electron 壳 | CI 依赖 vendor 的 apps/desktop | P2 决策（总方案允许「退役自建壳产物」）；P1 不动 release |

## 8. 下一步（P1 的可执行清单）

1. 根 `pnpm-workspace.yaml`（`packages/*/*`、`apps/*`）+ 根 `package.json` devDependencies 换成官方 `0.2.2-rc.3` 包。
2. `git mv` 迁出：`packages/starhub/*`、`apps/starhub-window → apps/starhub-workbench`、`packages/shims/client-runtime`、`profiles/starhub-{desktop,web,agent}`。
3. 根 `tsconfig.{base,host,client}.json`：**不再有 `paths` 别名指向源码**，`@deepseek-ai/dsh-*` 从 node_modules 解析；StarHub 包之间用 project references 排序。
4. 自建 `tsdown` 预设 + `apps/starhub-workbench` 的 vite 配置（只 alias 自有 `client-nav` 源码）。
5. 修 §1 的 6 个编译错误（全部是「把私有补丁/已删包的依赖换成本地定义」级别）。
6. 门槛：`tsc -b tsconfig.host.json`、`tsc -b tsconfig.client.json`、`build:window`、`plugin:bundle` 全绿，且 **`git grep vendor` 在 `scripts/ tests/ .github/` 里归零**。
